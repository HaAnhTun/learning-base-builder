## 98. Schema Design for Reliable Extraction

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 98/136 · en_US · auto caption

**[00:00]** Welcome back. Schema design is what this lesson is all about. The decisions that determine whether your extraction pipeline holds up under real inputs, how to choose between required and optional fields, how to write field descriptions that guide Claude's extraction decisions, strategies for handling missing data, nested schema patterns for complex documents, and how to test schema design before they hit production. Let's jump into it. Let's get the language right first. Required versus optional fields is the foundational decision.

**[00:27]** Required fields, the model always populates regardless of input content. Optional fields allow null or omission when data is genuinely absent, and getting this distinction right determines what downstream code can safely assume about your output. Enum constraints restrict a field to a defined set of valid string values, which matters any time a field drives routing logic or classification, and free text variation would break something. Nested schemas are structures where a field's value is itself an object or array with its own type and property definitions. They are the right tool for documents with hierarchical relationships, but they need to be designed as carefully as top-level fields. The required versus optional decision is probably the most consequential field-level design choice you make.

**[01:21]** If you mark a field required when the input doesn't always contain extractable data for it, the model will be pressured to produce something, and that something is often a hallucinated value that looks plausible but is wrong. If you mark too few fields required, you push all the validation burden to downstream code, which then has to handle unexpected structural variation at runtime. The right approach is to mark a field required only when the underlying data actually guarantees a value is present every time. Optional fields explicitly communicate to both the model and the downstream system that absence is a valid expected result, not an error condition. Field descriptions are the primary lever you have for guiding Clod's extraction decisions within a schema. A description that simply names the field, like the company name, gives the model almost nothing to work with when the document mentions a parent company, a subsidiary, and a brand name in different places.

**[02:18]** An effective description specifies what the field means in the context of the specific document type being processed. It defines the expected format, names boundary cases by describing what counts as a match and what doesn't, and indicates priority when multiple candidates exist. A well-written description resolves ambiguity before it becomes a wrong field value. The model reads the description as guidance during generation, so the precision of your language there directly affects extraction accuracy. Handling missing data is a schema design decision, not just an implementation detail. The null or omit strategy returns null or removes the field entirely when the data is genuinely absent.

**[03:06]** This makes absence explicit and distinguishable from a populated field, which is useful when downstream logic branches on whether a field has a value. It does require downstream code to handle none or missing keys without throwing an error. The default value strategy returns a sentinel like unknown or an empty string when data is absent, which produces a uniform output shape at the cost of making it harder to distinguish value was extracted from nothing was found. Neither strategy is universally correct. The right choice depends on how the downstream system handles absent data and whether the distinction between absent and populated needs to be preserved. Three field description patterns reliably undermine schema reliability.

**[03:47]** Too vague. A description like the name gives the model no basis for choosing when the document contains multiple names. The model is forced to make a judgment call that should have been a schema decision. No format specification, omitting the expected format for dates, identifiers, or status codes leads to inconsistent values that look correct but break parsers. Two different date formats in the same field across requests, for example, is a schema design failure, not a model failure. No boundary cases.

**[04:21]** Failing to define what counts as a match forces the model to reason from context alone about edge situations the schema author could have anticipated. Each of these anti-patterns creates variation that compounds in high volume production pipelines. Knee-stud schemas let you represent document structures with natural hierarchy. An invoice has line items, each with their own price, quantity, and description. A contract has parties, each with a name, role, and address. Object nesting is the right structure for any entity with its own coherent set of properties.

**[04:55]** Array of objects nesting handles repeating structures where the number of instances varies. The key discipline in nested schema design is to define required and optional fields for each nested object independently, just as you would for a top-level schema. The other discipline is knowing when to stop. Unnecessary depth makes schemas hard to maintain and test, and the model's ability to correctly populate deeply nested structures degrades as complexity increases. Nested schemas reflect document structure, but only as deep as the extraction task actually needs. Schema quality is the most controllable factor in extraction reliability, and it deserves to be treated as such.

**[05:35]** Clear field descriptions reduce ambiguous extractions when input phrasing varies across documents. Appropriate required versus optional settings prevent the model from hallucinating values for fields with no supporting content. Enum constraints eliminate the free text variation in classification fields that silently breaks downstream routing. Well-scoped nesting prevents the model from conflating separate entities or collapsing a nested structure into the wrong parent. Every schema design decision either increases or decreases the model's ability to produce consistent, correct output across varied inputs. Poor schema design doesn't cause visible errors at design time.

**[06:15]** It shifts the failure burden to downstream code that wasn't built to absorb it. Testing a schema before deploying it to production isn't optional if reliability matters. A missing field test runs the schema against input that lacks the field entirely and confirms the output is null or omitted rather than a hallucinated value. An ambiguous input test uses documents where two values could plausibly match a field, verifying that the field description guides selection to the intended one. A type boundary test uses values at the edges of expected types to verify the schema handles them correctly. Very long strings, empty strings, zero, and negative numbers.

**[06:56]** Each of these tests targets a specific failure mode that only appears under conditions that may not occur in your initial development set. Building a small edge case test library for each schema pays back quickly in production stability. Schema design is an active part of extraction quality. Required and optional fields set downstream expectations. Descriptions define context, format, and boundary conditions. Null and default strategies make absence explicit.

**[07:26]** Good schemas hold up across varied real-world inputs, not just clean examples. From here, we'll look at using tool definitions to extract structured data where schema enforcement happens at the argument level. I'll see you in the next lesson.

## 99. Structured Outputs Limits

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 99/136 · en_US · auto caption

**[00:00]** Structured outputs sound like a blank check, ask for JSON and always get valid JSON. But the guarantee only holds when your schema fits a supported subset. And a few constraints you write might never reach it at all. This lesson maps what works, what doesn't, and where the promise bends. Let's dig in. Structured outputs makes a strong promise.

**[00:24]** And that promise has an edge to it. Everything rests on the enforceable subset. The slice of JSON's schema, the grammar engine can actually compile and guarantee during generation, through constrained decoding. Write a keyword outside that subset and the raw API returns a 400 error, but the official SDK transforms it for you. It strips the keyword, folds its intent into the field's description, and validates the final response against your original full schema. Then there are the guarantee gaps.

**[00:55]** Two situations break the schema promise entirely, and both are expected behavior. Not bugs you should retry blindly. Everything else in this lesson hangs off those pieces. Let's start with the good news, the supported typeset. All of the standard JSON types are here. You've got the structural types, object and array, which let you nest and group.

**[01:18]** You've got the scalar types, string, integer, number, boolean, and null. And you've got enum and const, which pin a field to a fixed set of allowed values or a single constant. That combination covers most real extraction and classification work. If you're pulling fields out of a document or sorting something into categories, these types alone usually carry the whole schema. So the foundation is solid. Where it gets interesting is the layer above the basic types, composition.

**[01:47]** Composition is how you build richer shapes, and there are a few pieces to know. Any of lets the model pick one branch from several. That's how you express a union, where a field could be one shape or another. All of combines constraints together, but watch the catch. All of paired with a reference isn't supported. So don't lean on that pattern.

**[02:08]** Then you've got references. Internal ones, using $ref and $defs, let you define a shape once and reuse it across the schema, which keeps things clean. But external references, the kind that point at a remote URL, are rejected outright. So compose freely inside your own document. Just keep every reference local. Two smaller features round out what's supported, and both are narrow but genuinely useful.

**[02:36]** First, string formats. You can constrain a string to a shape like DateTime, PlainDate, Email, a URI, or a UUID. That's handy when you need a field to look like a real timestamp or identifier. Second, ArrayMinItems. You can require an array to be non-empty, but only barely, because the only supported values are 0 and 1. You can't say, give me at least 5.

**[03:01]** And RegX is supported at a basic level. Character classes, groups, and simple quantifiers. Anything richer than these falls outside the compiled grammar, which brings us to the full picture of enforced versus ignored. Here's the line that trips people up most, so let's draw it clearly. On the grammar-enforceable side, constrained decoding guarantees what the model can emit. That's your types, enum, const, anyof, allof, internal references, string formats, minItems of 0 or 1, and basic RegX.

**[03:35]** All of those really constrain generation. Everything else is the other bucket. Numeric bounds, minimum, maximum, and multiple of. String length, minLength, and maxLength. MaxItems. And additional properties, unless it's set to false.

**[03:51]** Send any of these to the raw API, and you get a 400 error. The official SDK handles it instead. It strips the keyword, folds its intent into the field description, and validates the final response against your original full schema. A few more constructs fall outside the grammar the same way. Recursive schemas, the kind that reference themselves to describe a tree or a nested comment thread. External references, pointing at a remote URL instead of a local definition.

**[04:21]** And complex RegX features, back references, lookAhead and lookBehind, and word boundaries. Send any of these to the raw API, and you get a 400 error. Exactly like the numeric and length keywords. The official SDK transforms them for you instead. But the practical move is to design them out from the start. Flatten a recursive structure into a bounded one.

**[04:45]** Inline your references, and keep patterns simple. That gives you a clean grammar, rather than leaning on the transform to bail you out. Next, the hard numeric limits. And these are worth memorizing, because they're easy to hit at scale. First, at most, 20 tools can carry strict mode in a single request. Non-strict tools don't count against that.

**[05:09]** Second, optional parameters. Across every strict schema and structured output in the request, you get a combined budget of just 24 optional parameters. That's a shared pool, so a handful of tools with 6 optional fields apiece already maxes it out. Third, union-typed parameters. Anything typed through any of, or a type array, like string or null, is capped at 16 total. The thing to notice is that these are request-wide budgets, not per tool, so complexity adds up faster than you'd expect.

**[05:44]** You met these two guarantee gaps in the structured outputs lesson. Here is what each one actually returns. The first is a refusal. If the request triggers a safety response, the model returns a refusal message, and safety wins over the schema. You'll see a stop reason of refusal, a normal 200 status, and build tokens, but the body won't match your shape. The second is a max-tokens cutoff.

**[06:10]** If generation hits the token ceiling, the output truncates. Don't assume it's still valid JSON. A truncated response can be incomplete and can fail to parse, because the closing braces and brackets may never get omitted. The fix is to check for a max-tokens stop reason and retry with a higher limit. In both cases, the first step is the same, check the stop reason before you trust the payload. Last piece, and it's about performance, not correctness.

**[06:39]** Your schema doesn't run as is, it compiles into a grammar first. That compile has real-timing behavior worth knowing. The very first request against a brand new schema pays a one-time compile latency, so that call feels slower. After that, the compiled grammar is cached for 24 hours from its last use, and repeat requests are much faster. Now, what busts the cache? Changing the schema's structure does, and so does changing the set of tools in the request.

**[07:09]** But here's a nice detail. Renaming a field or editing a description alone doesn't force a recompile. So cosmetic tweaks stay cheap, structural ones don't. The failure here doesn't look like a crash. It looks like a validator you wrote that quietly stopped being enforced, because the keyword you leaned on never made it to the grammar in the first place. Everything inside the supported subset really is guaranteed.

**[07:36]** Everything outside is just a suggestion. Just remember, a refusal or a truncated response breaks the promise, too. So read the stop reason before you parse. That wraps up this lesson. I'll see you in the next one.

## 101. Validation Loops and Hallucination Prevention

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 101/136 · en_US · auto caption

**[00:00]** If your extraction pipeline fails silently, the cost shows up in production. We're covering validation loops and hallucination prevention, the full loop pattern from extraction through re-prompt, the layers of validation that matter, how to design effective re-prompts on failure, and the grounding techniques that reduce confabulation in extraction pipelines. A validation loop is a programmatic pattern where extracted or generated structured output is validated against a schema or business rules after generation. On failure, the error is fed back into a follow-up prompt asking the model to correct its output. The loop continues until the output passes or a retry limit is reached. Hallucination prevention is a set of techniques that reduce the model's tendency to generate plausible but incorrect information.

**[00:49]** The techniques include grounding, citation instructions, schema constraints, and temperature settings. No single technique covers all failure modes. Grounding is the third concept, injecting source material or retrieved context into the prompt so the model is extracting from evidence rather than generating from memory, which is the most direct way to reduce confabulation. The validation loop pattern has four steps, and they matter in sequence. Step one, extract structured output using a tool call or the structured outputs feature, which constrains the response with an output config format schema. Step two, validate the output programmatically against your schema and business rules.

**[01:32]** Step three, if validation fails, construct a reprompt that includes the specific error details, the original source text, and a constrained correction instruction. Step four, send the reprompt and validate the new output. Repeat until it passes or the retry limit is hit. The key principle is that one-shot extraction without a retry path is insufficient for any pipeline where extraction errors have real downstream consequences. The exam tests this full loop sequence because it's common to see systems that add validation at the end without a reprompt path for when that validation fails. What you validate after extraction breaks into three layers, and each layer catches a different category of failure.

**[02:16]** Schema compliance is the first. All required fields are present, types are correct, and enum values are within the declared set. This layer is deterministic and automated. Business rule validation is the second. Values satisfy domain logic, such as dates falling within valid ranges, referenced identifiers existing in known sets, and numeric fields passing reasonableness thresholds. Schema validation can't catch these because a structurally valid value can still be semantically wrong.

**[02:46]** Semantic correctness is the third layer. The extracted values are consistent with the source text. Cross-field consistency checks belong here too, verifying that related fields don't contradict each other. Pipelines that only validate schema compliance miss the failures that matter most in production. The distinction between schema validation and business rule validation is the one that most extraction pipelines under-invest in. Schema validation is automated and deterministic.

**[03:14]** Does the output match the declared structure? It catches structural failures but can't tell you whether the values are meaningful. A date field typed as a string passes schema validation, whether it contains a real date or a hallucinated one. Business rule validation requires domain knowledge. Does the date fall within the valid range for this document type? Does the referenced identifier appear in the authoritative list?

**[03:36]** Are the numeric values within the range that is physically possible for this measurement? These checks require you to codify domain logic explicitly, but they are the layer that catches the failures that schema validation passes through. The combination of both layers is what makes a validation loop genuinely reliable. When validation fails, the reprompt design determines whether the next extraction attempt succeeds or continues to fail. Three principles make reprompts effective. First, include the specific validation error in the reprompt.

**[04:10]** Telling the model exactly what failed and what the expected value should be gives it precise guidance. A vague instruction like please correct the output without specifying the error gives the model no more information than the original prompt. Second, re-include the relevant source text so the model is re-extracting from evidence rather than attempting to correct its prior output from memory. Third, instruct the model to correct only the failing fields rather than regenerating the entire output. Full regeneration can fix the failing field but introduce new errors in fields that were previously correct. Targeted correction keeps the scope of the retry narrow and the risk of new errors low.

**[04:55]** Hallucination prevention requires multiple techniques because hallucinations arise from different failure modes. Grounding addresses the most common cause, the model generating plausible values from memory when the source text doesn't contain the needed information. Injecting the source document and instructing the model to extract only from it directly addresses this failure mode. Citation instructions make grounding violations auditable. When the model is asked to cite the specific source passage for each extracted field, unsupported extractions become visible. Schema constraints at the enum level eliminate out-of-vocabulary output by restricting the field to known valid values.

**[05:33]** Temperature reduction lowers output variance, which helps with consistency, but it doesn't address grounding gaps. No single technique is sufficient on its own because each one addresses a different failure mode. Grounding is the single most effective technique for reducing confabulation in extraction pipelines. The mechanism is straightforward. Inject the specific source document or retrieved passage into the prompt and instruct the model to extract only from that text rather than from general knowledge. When the model is operating on provided evidence rather than drawing on training data, the rate of fabricated values drops substantially.

**[06:10]** Citation instructions extend grounding by making the connection between extracted fields and source text explicit and auditable. For multi-document extraction, labeling each source with an identifier so the model's citations are traceable to specific documents is essential for downstream verification. The conceptual shift grounding enables is real. Extraction moves from memory-based generation, where the model fills gaps with plausible content, to evidence-based retrieval, where absence of evidence in the source produces an empty field rather than a fabricated value. Validation loops add latency and cost to every extraction pipeline, so the decision to use them should be intentional. **[03:26]** Which check failed? A brief explanation of why? And a suggested correction. That structure makes the critique immediately actionable in the revision step. Vague feedback from a reviewer produces vague revisions. Specific feedback produces specific improvements.

**[04:15]** Cost per eval is the total token spend divided by the number of cases which tracks whether the prompt is staying within operational budget constraints. **[03:46]** Code-based grading has four main techniques. Exact match is the simplest. The output equals an expected string, number, or value. **[04:00]** Nobody's waiting, the deadline is measured in hours, and a 24-hour ceiling fits inside it comfortably. There's one constraint that surprises people, and it's worth stating precisely because it's easy to get backwards. Batch requests do support tools.

**[04:38]** You can define them, and the model can return a tool call in the result. What you can't do is execute that tool and feed its result back partway through the request. A batch request is a single turn submitted once and returned once, so there's no round trip available to complete the loop in. That means the agentic pattern, where the model calls a tool, reads what came back, and decides what to do next, needs the synchronous path. Batches suit single-turn work, however much of it you have. Three practical points to close on.

**[05:11]** Batching stacks with your other cost controls rather than replacing them. If every request in the batch shares a large system prompt, that prompt still caches across them, so the discount and the cache-saving compound. And before you commit 10,000 documents, run the prompt over a small sample and check the output. A first pass failure at full volume means paying for the whole run, and then paying again for the resubmission. Size your submissions against your own deadline, too. If a result is needed by 9 in the morning, submitting at 8 and hoping for the typical case isn't a plan, because the ceiling is what you're actually promised.

**[05:50]** The expensive mistake with batching isn't the weight. It's assuming results come back in the order you sent them. They don't, and a positional read fails quietly, so wrong answers land on right records and nobody notices for weeks.

## 50. STDIO Transport — Local Servers and Process Communication

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 50/136 · en_US · auto caption

**[00:00]** When you're choosing how an MCP client talks to a server, STDIO is one of two primary options. It spawns the server as a subprocess and exchanges messages through stand-in and stand-out. Let me walk you through how that works, when it's the right choice, and why Cloud Code uses STDIO natively. STDIO transport works because of something every process already has. When a program starts, the operating system hands it standard streams, stand-in for input, stand-out for output, and stder for errors. STDIO transport uses stand-in and stand-out as a bidirectional pipe for MCP messages, which is why it needs no network configuration at all.

**[00:45]** The other half of the picture is the child process. A child process is one that a parent process spawns and manages. And in this model, the MCP client is the parent, and the server is the child. So the client launches the server, keeps hold of its streams, and talks to it directly. That relationship is the whole transport. Here's how STDIO transport actually works at the process level.

**[01:11]** When the client starts, it reads its configuration to find the command that launches each registered MCP server. It then spawns those servers as child processes, using the operating system's standard process creation facilities. Once the child is running, the client and server exchange new line delimited JSON messages. Client writes to the child's stand-in. Server reads from its own stand-in and writes responses to stand-out. Client reads from the child's stand-out.

**[01:40]** That's the entire communication model. There's no socket, no port, no HTTP layer. The OS process table and pipe infrastructure handle everything. This is fast, simple, and completely self-contained on a single machine. The contrast between STDIO and network-based transports is sharper than it looks. STDIO uses OS-level pipes, not the network stack.

**[02:05]** There's no port to bind, no firewall rule to configure, no TLS certificate to manage. It's inherently single user because the process is private to the client that spawned it. Network transports do the opposite. The server binds to a port, listens for connections, and handles authentication and encryption to safely serve multiple clients. Network transport is more complex to deploy and operate, but it's the only option when the client and server aren't on the same machine. STDIO is simple precisely because it gives up everything that network transport offers.

**[02:45]** STDIO fits best in three situations. Local development is the obvious one because running an MCP server as a subprocess on your dev machine is the fastest iteration loop while you build and test. Desktop tool integrations are another, since an application that bundles its own server always has both components on the same machine. Then there is Cloud Code, which supports STDIO for local MCP servers and falls back to HTTP or SSE for remote ones. You register a local server in Cloud Code settings with the command that launches it, and Cloud Code spawns it as a child process at session start. What STDIO can't do matters just as much.

**[03:28]** The moment a use case needs access from another host or a second simultaneous user, STDIO is the wrong transport. Three characteristics define STDIO deployments. Zero configuration means there's nothing to set up on the network side. The OS handles the pipe. Single user scope means one server process per client instance. There's no concept of sharing.

**[03:52]** And subprocess lifecycle means the server starts when the client spawns it and exits when the client exits. These three properties work together. Because each client owns its process, and that process lives only for the session, there's no shared state between clients, no port conflicts, and no cleanup problem when a client disconnects. The simplicity is a feature when you're operating in the right context. But each of these properties is also a constraint. State management in STDIO is straightforward.

**[04:24]** Because one server process is tied to one client session, the server can keep state in memory across all tool calls within that session. You don't need to serialize state to a database between calls because the process stays alive. A tool call made early in the session can produce a result that a later call reads from memory. When the client exits, the process exits, and all in-memory state is released. There's no risk of stale session state leaking to another user because each user gets their own process. This model simplifies server implementation significantly.

**[05:02]** But it means STDIO can't serve a shared cache or shared resource across multiple clients. STDIO has three limitations that are important for the exam. No remote access. Because the server is a subprocess, it's physically inaccessible from any other host. There's no address to connect to. No multi-user sharing.

**[05:25]** Each user gets their own process. Sharing a single STDIO server across clients isn't architecturally possible. And STDIO isn't appropriate for production API deployments. If you're building a server that multiple users or multiple applications need to reach over a network, STDIO isn't the right transport. These aren't bugs. They're design choices that make STDIO simpler.

**[05:51]** But they do define a clear ceiling on where STDIO applies. A local MCP server under STDIO is really just another child process. The client owns its entire lifetime. There's no port to open and no session to resume because when your client goes away, the server goes with it. Almost everything else about STDIO falls out of that single relationship. That's it for this one.

## 51. StreamableHTTP Transport — Remote Servers and Production Deployment

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 51/136 · en_US · auto caption

**[00:00]** Streamable HTTP is what happens when stdio falls short. It turns an MCP server into a network accessible HTTP service using server sent events for streaming, and it supports both stateless and session-based state. Here's what you need to know to pick the right transport for any deployment context. The moment a server has to be reachable from another machine, the transport has to become a real network service. That is streamable HTTP transport. It runs the MCP server as an HTTP service and supports both standard request response and streaming, and it's the current standard for remote and production deployments.

**[00:39]** The streaming half comes from server sent events, or SSE, a unidirectional HTTP protocol where the server pushes a sequence of events to the client over a long-lived connection. Then there's stateless HTTP, the request model where each call carries all the context it needs, so the server stores nothing between calls. Streamable HTTP supports that model and a session-based one, and we'll look at both. Streamable HTTP works by turning the MCP server into a standard HTTP service. The server binds to a port and exposes a single endpoint. To make a tool call, the client sends one HTTP post containing the MCP message.

**[01:23]** Here's the key detail. The server decides how to respond. It can reply with a plain JSON body, or it can upgrade that same response to a server sent events stream, pushing progress notifications first and then the final result. So the server initiates streaming, not the client. Separately, the client also opens a long-lived HTTP get connection, which gives the server a channel to push its own notifications and requests to the client. One endpoint, both directions covered.

**[01:55]** Server sent events is the streaming mechanism inside streamable HTTP, and it's worth understanding how it works at the protocol level. The client sends an HTTP request that stays open. Instead of sending a single response and closing the connection, the server keeps writing event frames to the response stream as they become available. Each event frame follows the SSE text format, a data field containing the event payload, terminated by a blank line. The client reads these frames as they arrive. This is unidirectional.

**[02:28]** The server pushes, the client receives. The client can't send messages over the same connection. For MCP, SSE is used to stream progress notifications back to the client while a long-running tool operation is still executing on the server. Streamable HTTP lets you choose between two state management approaches, and the choice has real scalability implications. Stateless HTTP means each request is completely self-contained. The client sends all the context it needs in the request body, and the server returns a result without storing anything between requests.

**[03:08]** Because no per-client state exists on the server, any server instance in a load-balanced pool can handle any request. This scales horizontally with no coordination overhead. Session-based state means the client sends a session token, and the server maintains a context store keyed to that token. This supports multi-turn interactions, where the server needs to remember what happened in earlier calls. It works, but it requires sticky sessions or a shared state backend to function correctly behind a load balancer. Three scenarios point clearly to streamable HTTP as the right choice.

**[03:46]** Remote clients. If the client and server are on different machines, you need an HTTP-based transport. There's no alternative because STDIO can't cross a network. Multi-user deployments. A single streamable HTTP server can handle concurrent connections from multiple clients. There's no need to spawn a dedicated process per user.

**[04:13]** Production APIs. HTTP gives you the entire production infrastructure stack. TLS for encryption, bearer tokens, or API keys for authentication, and load balancers for traffic distribution. These are things you'd have to build a completely separate layer for if you were using STDIO, and none of them would work remotely anyway. There's a naming point worth flagging here. In the older 2024-11-05 version of the MCP specification, there was a separate transport called HTTP plus SSE that has changed.

**[04:46]** Current MCP consolidates streaming under the streamable HTTP transport, and the old HTTP plus SSE transport is deprecated. So SSE today is the streaming delivery mechanism inside streamable HTTP, not a standalone peer to it. If you see the deprecated HTTP plus SSE name presented as a current separate option, the correct framing is that it's been folded into streamable HTTP. The transport that supports streaming in current MCP is streamable HTTP, full stop. When you deploy an MCP server over streamable HTTP in production, you take on standard HTTP service responsibilities that don't exist for STDIO. TLS is the first requirement.

**[05:39]** If the server is reachable over any untrusted network, all traffic should be encrypted. Authentication is the second. Every client request should carry a credential, either a bearer token or an API key, that the server validates before processing the MCP message. Load balancing is the third. A production server handling concurrent clients should be able to distribute load across multiple instances. All of this is standard infrastructure for any HTTP service, but it's a meaningful operational step up from the zero configuration model that STDIO provides.

**[06:17]** Let's make the transport selection decision concrete. Use STDIO when the server and client are on the same machine, when you're serving exactly one user at a time, and when you want zero network configuration. Local development tools, desktop applications that bundle their own MCP server, and cloud code integrations all fit this pattern. Use streamable HTTP when the client needs to reach the server over a network, when multiple users or multiple client applications need to share the same server, or when you need production infrastructure like TLS and authentication. The decision rule is simple. If the deployment crosses a network boundary or serves more than one user, STDIO is eliminated from consideration.

**[07:02]** People treat SSE and streamable HTTP as competing options on the same menu. They really aren't. Streamable HTTP is the transport, and server sent events is what the transport uses when a response needs to arrive in pieces rather than all at once. Get that relationship backwards, and you'll go hunting for a setting that was never really a transport to begin with. That's where we'll leave it on this one. I'll see you in the next lesson.

## 52. Letting Servers Make LLM Calls Through the Client

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 52/136 · en_US · auto caption

**[00:00]** Sampling is one of MCP's most advanced features, and it's worth a detour. It lets a server ask the client to make an LLM inference call and send the results back. Coming up in this video, we'll cover why this design choice keeps control where it belongs, and how to implement a sampling handler in your own MCP client. Let's jump into it. Picture a server that needs a summary written, but has no model of its own, and no API key. That is the problem sampling solves.

**[00:32]** Sampling in MCP is the pattern where a server sends a create message request to the client, the client calls an LLM on the server's behalf, and the result comes back over the MCP channel. The piece that makes it work on the client side is the sampling handler, a callback you register that receives the request, calls your LLM API, and returns the model's response. And there's an optional human-in-the-loop gate, an approval step where a user can review the request and accept or reject it before the model is ever called. Why does sampling exist at all? The answer is about separating concerns cleanly. A well-designed MCP server is stateless and focused on its domain, covering file operations, database queries, and web search.

**[01:18]** It shouldn't need to hold its own LLM API credentials or worry about which model to use. The client already has that relationship. It has credentials, it knows the user's preferred model, and it enforces policy about what data can go to the model. Sampling reuses all of that existing infrastructure. Instead of every server independently managing model access, which multiplies credential sprawl and policy gaps, sampling centralizes that control. The client becomes the single control point for all model calls in the system.

**[01:53]** That's cleaner architecturally and much easier to audit. Let's walk through the sampling flow step-by-step so it's clear what happens at each stage. First, the server decides it needs LLM assistance and sends a create message request to the client over the standard MCP channel. That request includes the messages it wants processed, an optional system prompt, and any model preference hints. Second, the client receives the request. If human in the loop is configured, it pauses and shows the user the pending request for approval.

**[02:29]** Third, the client calls the API once approved, or immediately if no approval gate is set. Fourth, the model's response comes back to the client, which packages it as a standard MCP result and returns it to the server. The server then uses that result just like any other tool response. One of the most important things to understand about sampling is the distinction between what the server controls and what the client controls. The server owns the message content. It decides what question to ask, what context to include, and what system prompt to use.

**[03:04]** It can also express model preferences, but the client owns the actual model selection, the credentials, and the data policies. This division is intentional. It means a server operator can't unilaterally choose an expensive model or route-sensitive data to an unapproved endpoint. The client owner, meaning the person deploying the agent, always has the final say. That separation is what makes sampling safe to enable in production systems. Implementing a sampling handler in Python is straightforward with the MCPSDK.

**[03:36]** You define an async function that accepts a createMessageRequest object, which contains the messages list, the optional system prompt, and the model preferences. Inside that function, you call your LLM API. In most cases, that means the Anthropic API. Using the message content from the sampling request, you then wrap the model's text response in a createMessageResult and return it. You register this function on the client before connecting to any servers, and the SDK automatically routes incoming createMessageRequests to it. The handler is the only code you need to write.

**[04:13]** The SDK handles all the serialization and protocol routing around it. To make the difference concrete, compare sampling to giving a server its own API key. With direct access, the server calls the LLM independently using its own credentials. You lose visibility into those calls, you can't enforce model selection policy, and credentials multiply across every server you deploy. With sampling, all of that disappears. The server never touches an API key.

**[04:43]** Every inference request flows through the client, which means every call is visible, logged, and subject to the same policies. If you want to swap models, you change it in one place. If you want to audit what's being sent to the LLM, you have a single choke point. Sampling is simply the more secure and maintainable design for any non-trivial deployment. When a server sends a createMessageRequest, it can include model preferences. These aren't hard requirements, they're suggestions.

**[05:14]** There are three priority values, each a number from 0 to 1. Cost priority says how much minimizing spend matters. Speed priority says how much low latency matters. Intelligence priority says how capable the model needs to be. The server can also send hints, which are model name substrings The client matches flexibly and evaluates in order. The key constraint is that the client is always free to honor, substitute, or ignore all of this.

**[05:42]** If the user's policy says only one model is approved, that's what gets used regardless of server preferences. Preferences let servers communicate needs without demanding control, which keeps the client firmly in charge. Human-in-the-loop sampling is a practical safety feature, especially during development or when servers are requesting access to sensitive content. When it's enabled, the client doesn't immediately forward the sampling request to the LLM. Instead, it surfaces the full request so the user can review and approve it, including the messages the server wants to send to the model. The user reviews it and either approves, edits, or rejects it.

**[06:24]** Only approved requests move forward. This means a misconfigured or malicious server can't silently pump sensitive data into a model call without the user noticing. For production systems handling regulated data, human-in-the-loop can also serve as a compliance checkpoint, giving you an auditable record of every approved model interaction. It's easy to conflate a server having intelligence with a server having model access. Sampling separates them. The server asks for an inference, and the client is the one who picks the model, spins the tokens, and decides whether a human sees it first.

**[07:04]** That's why you can hand a server real reasoning power and still have exactly one piece to audit. That's it for this lesson. I'll see you in the next one.

## 53. Notifications, Roots, and Progress Reporting

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 53/136 · en_US · auto caption

**[00:00]** If you're building MCP servers that run in production, log notifications, progress notifications, and routes are the three features that matter most. They let servers communicate status during long-running operations and give servers controlled, scoped access to the client file system without opening up a security loophole. Let's go through each one now. A slow tool call and a hung tool call look exactly the same from the client side, and that ambiguity is what these features fix. A progress notification is an MCP notification a server sends during a long-running tool call to report incremental status. It carries a numeric progress value and an optional total, so the client can compute a percentage for the user.

**[00:44]** A log notification carries diagnostic text with a severity level, such as info, warning, or error, plus an optional logger name. And routes are the list of file system paths, or URIs the client advises a server to work within. Routes communicate intended scope, but they are advisory because the protocol doesn't enforce them. The standard MCP tool call model is synchronous. The client sends a request and waits for the result. For tools that finish in milliseconds, that's completely fine, but for tools that process large files, run database queries, or make external API calls, the client can be waiting for seconds or even minutes with no feedback.

**[01:30]** That silence creates a bad user experience and makes it hard to diagnose problems when something goes wrong. Notifications break that silence. The server sends status updates as the operation progresses, and the client can display them, log them, or surface them to the user in real time. Think of notifications as the MCP equivalent of a progress bar. They transform an opaque weight into an observable process. Log notifications are the simpler of the two notification types.

**[02:02]** They carry a severity level, a logger name, and a message string. These are the eight standard size log severity levels. Debug, info, notice, warning, error, critical, alert, and emergency, in increasing order of urgency. The server sends these whenever it wants to surface diagnostic information to the client. The client can display them in a log pane, filter by severity threshold, store them for later review, or ignore them entirely. Log notifications are fire and forget.

**[02:32]** They don't expect a response, so a server can omit them during any operation without blocking. You call a single context method and the MCP framework handles the rest, especially valuable during development when you want step-by-step visibility into what a tool is doing. Progress notifications have a slightly more structured format because they're designed to drive UI elements like progress bars. Every progress notification includes a progress token, an opaque identifier from the original tool call request. That token ties the update to its parent operation, so the client knows which tool call is reporting. The progress field is a numeric value indicating how far along the operation is.

**[03:15]** The total field is optional. Include it, and clients can divide progress by total to get a percentage. Leave it out, and the client shows an indeterminate indicator. The convention is to call report progress at meaningful checkpoints after each major step completes, not on every minor iteration. That way the client always has a current view without being flooded with updates. Wiring progress notifications into a tool is straightforward.

**[03:44]** When the client sends a tool call request, it can include a progress token in the meta field. Inside your handler, you check for that token. If it's present, you call CTX report progress at each meaningful step. The MCP server framework serializes the notification and sends it to the client automatically. You don't manage the transport yourself. One important detail.

**[04:02]** If the client didn't include a progress token, it means the client doesn't want progress updates for this call. Skip the report progress calls. Clients that don't support progress notifications won't send tokens, and your tool degrades gracefully with no special handling required. It's worth comparing log and progress notifications directly because developers sometimes reach for the wrong one. Log notifications are for diagnostic text, meaning messages that tell you what the server is doing and whether it's healthy. They're tagged with severity so they can be filtered and stored.

**[04:46]** Progress notifications are for numeric status tied to a specific operation. They're designed to drive a progress indicator in the user interface. You wouldn't use a log notification to update a progress bar, and you wouldn't use a progress notification to surface an error message. In a production server, you'll typically use both log notifications for observability and debugging. Progress notifications for user-facing feedback during long operations. Roots are how MCP communicates file system scope, and here's what people get backwards.

**[05:13]** It's the client, not the server, that declares the root's capability during initialization. The server then requests the list by calling roots slash list, and each root is a URI. Those roots are advisory. They tell a well-behaved server where to confine itself, but the protocol never stops one from reaching outside. That matters most when servers come from different vendors, and you don't want a third-party tool reading files beyond its expected scope. The protection has to be layered underneath through restricted operating system permissions, a sandbox around the server, or the client validating paths before it acts.

**[05:56]** Roots make the intended scope explicit and auditable. The enforcement is your job. When a long-running tool goes quiet, what the user actually sees is a client that looks hung up, and what you see in triage is nothing at all. That's the gap these features close. One carrying diagnostic out, and one carrying progress back. Roots are the odd one out.

**[06:24]** They tell a server where to stay, but they don't enforce it, so the real boundary still lives in your permissions file. That closes out this lesson. I'll see you in the next one.

## 54. Tool Boundaries, Access Scoping, and Least Privilege

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 54/136 · en_US · auto caption

**[00:00]** Every tool you define on an MCP server creates a trust boundary, meaning a set of permissions the model can exercise on behalf of the user. That framing changes how you approach tool design. Let me walk you through the least privilege principle, access scoping mechanisms, and input sanitization at the server boundary. Picture an MCP server that can reach every file on the host machine. That is the failure mode the rest of this lesson works to prevent. Access scoping is the discipline that prevents it, defining explicit boundaries on what data, systems, and operations each server and its tools may reach, enforced through schema constraints, server-side authorization, and operating system permissions.

**[00:44]** Least privilege narrows each tool to the permissions its specific function requires, and nothing more, which keeps the blast radius small when a tool is misused. Input sanitization validates and cleans every argument arriving at the server boundary before it reaches any downstream system, which is where injection attacks get stopped. Why should you think of a tool definition as a trust boundary? Because the schema and handler together define the full scope of what the model can do when it invokes that tool. The schema sets the expected argument types. The handler determines which systems the tool connects to and what operations it can perform.

**[01:25]** If you define a tool loosely, accepting freeform inputs and connecting to everything, you create a large and poorly controlled attack surface. You've effectively handed the model and anyone who can influence its outputs a very broad set of permissions. Treating every tool as a boundary forces you to ask, during design, exactly what should this tool be allowed to do and what should it explicitly not do? That question, answered honestly for every tool, is how you build an MCP server you can actually defend. Applying least privilege to MCP tools starts with a simple rule, one tool per logical operation. A read-only search tool should have no write permissions at all.

**[02:09]** A tool scoped to one database should have credentials that only reach that database. A file tool should be bound to specific directory paths, rather than having access to the full file system. When you give each tool the minimum access it needs for its purpose, you shrink the blast radius of any misuse. If the model is manipulated into calling a tool in an unexpected way, or if the MCP server itself is compromised, narrow scope limits how much damage can result. Least privilege isn't just a security checkbox. It's a design discipline that makes the system easier to audit and reason about over time.

**[02:46]** MCP gives you three concrete mechanisms to enforce access scoping. Schema constraints are the first layer. Declare a strict enum for an argument, and the server rejects inputs outside that set before your handler logic ever runs. Server-side authorization is the second. Even after the schema validates the input, your handler checks the caller's identity and permissions before touching any downstream resource. Operating system permissions are the third.

**[03:15]** File system and process limits, on the host cap, what the server can actually reach. It's worth clearing up roots here, because people mistake them for enforcement. Roots are an advisory signal. A client advertises the directories it wants a server to focus on, and a well-behaved server should honor them, but nothing forces it to. Real enforcement lives in those three layers. Broad scope versus narrow scope illustrates why this matters.

**[03:44]** A tool that accepts any SQL string and connects to any database gives the model complete data access. An attacker who can influence the model's outputs, through prompt injection, for example, can potentially redirect tool calls to extract, modify, or delete arbitrary data through that one tool. A narrow design replaces that single permissive tool with multiple specialized ones. One for reading a specific table, with schema-constrained filter arguments. Another for a different table with its own constraints. Each tool connects with credentials, scoped to its purpose.

**[04:22]** If any single tool is abused, the damage is contained to what that tool can reach, which by design is very little. Input sanitization happens at the server boundary, and it should happen before any handler logic runs. Every argument arriving at an MCP server should be treated as untrusted input. Regardless of where the client claims it came from. The first step is type and format validation against the declared schema. If the schema says an argument is an integer, reject anything that isn't.

**[04:52]** The next step is sanitizing or escaping characters that have special meaning in the downstream system. SQL wildcards, shell metacharacters, path traversal sequences. Length limits matter too. An unbounded string argument can cause resource exhaustion, or expose buffer overflow risks in downstream code. Server-side sanitization is the last defense before your tool handler reaches production systems. Designing tools with least privilege means making access decisions before you write a single line of handler code.

**[05:27]** Define one tool per logical operation, not one tool per domain. Use enum constraints wherever possible so the model can only select from a valid pre-approved set of values. Filter the results your tool returns to include only what the caller is actually authorized to see. Don't return raw database rows and hope the host application filters them. Tools designed this way are narrow, auditable, and safe by default. Tools designed without this discipline may work correctly in normal use, but they're brittle under adversarial conditions and hard to secure after the fact.

**[06:06]** A few scoping mistakes come up repeatedly in MCP server designs. The first is overly permissive schemas. Using free-form string arguments where an enum would work allows the model to craft arbitrary downstream queries. The second is shared credentials. When all tools on a server share one set of backend credentials, any tool's compromise exposes every system those credentials can reach. The third is missing output filtering.

**[06:35]** Returning raw query results without filtering can expose records the calling user has no right to see. Each of these is a design decision that feels harmless in a development environment, but creates significant exposure in production. Fixing them early during tool design is much cheaper than auditing and remediating them later.

**[06:57]** When a tool's scope is too wide, you don't see it fail. You see it work. On data, it was never meant to reach. That's the uncomfortable part. A tool definition is a grant of permission, and the model will use every bit of reach that you give to it. Narrow the grant, and one compromised tool stays one compromised tool instead of compromising the entire system.

## 55. MCP in Production — Authentication, Versioning, and Reliability

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 55/136 · en_US · auto caption

**[00:00]** When you're deploying an MCP server to production, development assumptions break fast. Development servers trust the local process. Production servers need to answer harder questions. Who's calling? Are they authorized? How do you handle multiple client versions?

**[00:17]** And what happens under load? In this lesson, we'll work through authentication, versioning, rate limiting, and monitoring. Let's get into it. A production MCP server has to answer for itself in ways a local one never does. MCP authentication is the mechanism by which a client proves its identity to a remote MCP server before accessing tools and resources. For remote streamable HTTP servers, MCP defines an optional OAuth 2.1-based authorization flow as the recommended mechanism.

**[00:52]** Simpler options like API keys still work, but OAuth is the standardized path the spec points you toward. Semantic versioning uses major, minor, and patch numbers to signal how much a change breaks existing consumers. A major bump means breaking changes. Minor means new features that are backward compatible. Patch means bug fixes. And rate limiting is capping how many requests a client or user can send per unit time, protecting shared infrastructure from overload, and preventing one client from crowding out all the others.

**[01:27]** A local MCP server running on a developer's machine can trust the process that called it. There's no network boundary to cross. A remote production server is completely different. Any client that can reach the endpoint over the network could try to invoke its tools. Without authentication, there's no way to know who is calling. There's no stable identity to attach to audit logs, and no foundation for authorization decisions.

**[01:53]** You can't limit which tools a client can invoke if you don't know who the client is. Authentication is the prerequisite for everything else in a secure production deployment. It enables authorization, meaningful logging, and per-client rate limiting. A production MCP server without authentication is essentially a public API for every tool it exposes. MCP's specification defines an optional OAuth 2.1 authorization flow as the recommended mechanism for remote streamable HTTP servers. The flow works as you'd expect.

**[02:29]** The client goes through an OAuth authorization flow with an identity provider to obtain an access token. That token is included with each request to the MCP server. The server validates the token and reads the scopes it carries. Crucially, those scopes can map directly to which tools the client is allowed to invoke. A token with a read-only scope should only be able to call read tools. This design keeps the MCP server stateless.

**[02:57]** It doesn't manage sessions or store credentials itself. The identity provider handles that complexity, and the MCP server just validates tokens on every request. OAuth 2.1 is the answer to reach for when the question involves authenticating clients to a remote streamable HTTP MCP server, but it's useful to understand the alternatives and why they fall short for this use case. API keys are simple shared secrets passed in request headers. They're easy to implement but provide no per-user identity, no scope granularity, and no standard revocation flow. A shared key can't tell you which user made a call.

**[03:37]** Mutual TLS, or MTLS, authenticates both client and server using certificates. It's strong for service-to-service scenarios, but adds certificate management overhead that most MCP deployments don't need. OAuth handles the human-in-the-loop case where an actual user needs to authorize a client to access tools on their behalf. Before we leave authentication, there's a set of transport-level security rules the MCP specification is unusually firm about for streamable HTTP servers, and they're easy to miss. First, the server is required to validate the origin header on every incoming connection. This is what stops a DNS rebinding attack, where a malicious web page tricks a browser into talking to your server.

**[04:25]** Second, when the server runs locally, it should bind only to the loopback address, 127.0.0.1, rather than to all network interfaces. Binding to everything exposes a local server to the whole network. Third, the server should authenticate its connections. Notice the strength here. Validating origin is mandatory in the spec. The other two are strong recommendations.

**[04:52]** Versioning MCP servers is about managing change without breaking clients that depend on tools that already exist. The rule is straightforward. Backward-compatible changes don't require a version bump that breaks clients. Adding a new optional tool, adding optional fields to an existing schema, or fixing a bug in a handler while clients that haven't updated continue working exactly as before. Breaking changes are different. Removing a tool, renaming it, or changing required argument names or types will break any client that calls that tool.

**[05:32]** These need a major version bump, a migration window, where both old and new versions are served simultaneously, and explicit deprecation notices before the old version is retired. The pattern is the same as any other API. Communicate changes early and give clients time to adapt. Rate limiting is how a shared MCP server stays healthy when multiple clients are hitting it simultaneously. Without limits, a single client running a heavy batch job can saturate the server's resources and make it unresponsive for everyone else. The baseline practice is a per-client cap, on requests per time window.

**[06:11]** Beyond that, expensive operations need their own tighter limits. A tool that makes external API calls or runs database queries has a different cost profile than a tool that does a simple lookup. When a client hits a limit, the server should return an HTTP 429 response with a retry after header, so the client knows when it can try again. Rate limits make infrastructure costs predictable and protect all clients equally. Monitoring a production MCP server means treating it like any other API service in your stack. Every tool invocation should generate a log entry that captures the caller's identity, a sanitized summary of the arguments, the result status, and the end-to-end latency.

**[06:57]** With that data, you can track error rates by tool and detect when a downstream dependency starts degrading. You can set alerts when error rates or P99 latency breach thresholds you define. You can review access patterns to spot unexpected usage or potential misuse. Visibility into which tools are being called, by whom, and at what frequency is also directly useful for capacity planning. Without this observability, you're operating a production service blind. Three reliability practices every production MCP server needs.

**[07:32]** First, a dedicated health endpoint that load balancers and uptime monitors can pull without invoking real tools. This lets infrastructure verify the server is responsive without creating side effects in the tools themselves. Second, graceful degradation when a downstream dependency is unavailable. Return a structured error result instead of crashing or hanging, so clients can retry or fall back without a hard failure. Third, hard timeouts on tool handler execution, so a slow downstream system can't hold a connection open indefinitely and exhaust the server's connection pool. These three practices cover the most common production failure modes, health checks, graceful errors, and timeouts.

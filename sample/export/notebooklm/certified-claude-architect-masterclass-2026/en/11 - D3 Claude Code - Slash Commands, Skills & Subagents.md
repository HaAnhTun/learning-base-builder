Every command you build forces the same set of decisions, how much it should do, what to call it, and how it reaches your teammates. Narrow scope command means a command designed to do exactly one thing, the single responsibility principle applied to slash commands. Verb-noun convention is the naming pattern you'll see in the best command libraries, slash review-pr, slash run-tests, slash explain-file. The verb states the action and the noun states the target.

**[00:52]** Someone new to the team can read the keyword and know what the command does before they ever open the file. It carries commands too, so admins push them to every user in an organization automatically. Each of these connects to a concrete decision you'll make when building a command library. The number one design rule for slash commands is narrow scope. A command that does one thing is predictable, easy to maintain, and composes well with other commands.

**[01:29]** A command that does many things, say, it reviews the pull request, runs the test suite, and suggests a deployment strategy all in one go is a problem waiting to happen. The instruction template becomes a multi-paragraph tangle. Claude has conflicting signals about what to prioritize. Users don't know what output to expect. And when something goes wrong, it's hard to tell which part of the template caused it. Build small, focused commands.

**[01:56]** Compose them when you need to cover more ground. Every command file is a system prompt. Four elements make a system prompt effective when it's used as a reusable command. First, role. Tell Claude what perspective it's operating from. You are a senior engineer reviewing for security issues.

**[02:16]** Second, task. Describe exactly what to do. Review the diff passed as args. Third, output format. Specify how the response should be structured. Return findings as a bulleted list, grouped by severity.

**[02:28]** Critical, high, low. Fourth, constraints. What to exclude, what tone to use. Any scope limits. Missing any of these leads to output that varies unpredictably across runs, which defeats the entire point of having a reusable command. The choice between freeform args and a structured template comes down to how much shape the input needs.

**[02:56]** Freeform works perfectly when a single piece of text is all you need. Slash explainfileapp.py passes one file name. Clean, low friction, no setup. A structured template is better when input has multiple fields, or when getting the shape wrong would cause errors. In that case, write the template to explicitly prompt for each piece. Provide your PR number, reviewer role, and primary focus area.

**[03:25]** Users follow the template rather than guessing. The overhead of structure pays off when the command is complex enough that incorrect input would produce meaningless or misleading output. Naming conventions matter more than they seem. The verb-noun pattern, slash review-pr, slash run-tests, slash explainfile, slash generate-changelog, is the standard because it's self-documenting. Anyone reading the command list can infer what each command does without opening a single file. Contrast that with slash-pr, slash-code, or something worse like slash-do-it.

**[04:01]** Those names tell you nothing. You have to read the file to understand what the command does, and even then, you might not be sure. A consistent naming convention across a team's command library creates a shared vocabulary. New teammates can guess the right keyword before they've even read the documentation, and that's exactly the outcome you want. Team distribution for project-scoped commands is essentially free. You commit .clod slash commands to version control as part of the project, and from that point forward, every developer who clones or pulls the repo has the full command library.

**[04:37]** Updates work the same way. Improve a command, commit, and the update propagates via normal pull and merge. There's no separate sharing mechanism, no configuration management layer, no documentation to update about where the files live. The commands travel with the codebase. This is one of the most underappreciated properties of the project-level scope. The distribution channel already exists.

**[05:01]** You're just using it. For organizations running clod code at scale, managed settings provide a centralized distribution mechanism. Administrators configure commands at the organization level, and those commands are pushed automatically to every user in the organization. Users don't need to do anything. They can't accidentally delete org-level commands or override them with personal files. This matters most for commands that enforce compliance workflows, or organization-wide automation standards.

**[05:33]** When you want to guarantee that every developer in a 1,000-person org has access to the same slash review for compliance command, managed settings is how you do it without relying on every team to maintain their own copy. Two anti-patterns come up constantly when teams start building command libraries. The first is the overly broad command. Someone builds slash do-everything that reviews, refactors, tests, and deploys in one file. It works occasionally and fails confusingly. Narrow the scope.

**[06:06]** The second anti-pattern is duplicating clod.md instructions inside command files. clod.md already provides standing context at the session level. Commands should extend and build on what clod.md establishes, not repeat it. These two patterns, overbroad scope and instruction duplication, are the most common ways command libraries become unreliable.

**[06:41]** Effective slash commands keep a narrow scope, use verb-noun naming, and reach the team through version control or managed settings. Freeform arguments works when a single piece of text is all you need, and a structured template earns its keep when the input has shape and getting it wrong would cost you. Avoid the command that tries to do everything and avoid copying clod.md instructions into a command file where they'll quietly drift apart. That's it for this lesson. I'll see you in the next one.

## 73. What Skills Are and When to Build Them

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 73/136 · en_US · auto caption

**[00:00]** Skills are what you build when you want a procedure Claude pulls in automatically whenever it fits a request, without someone having to remember to type a command. Over the next few minutes, we'll look at how skills differ from slash commands and sub-agents, the decision framework for choosing to build one, and where skills sit in the broader instruction stack. Let's dive in. Claude code gives you more than one way to package a repeatable instruction, and picking the wrong one is how workflows get over-engineered. A skill is a reusable instruction package, a skill.md file plus any optional supporting files. Claude loads it automatically when its description matches what you're asking for, or you invoke it directly by name.

**[00:44]** A slash command is really a subset of skills now, created in the.claude commands directory, and invoked with a slash name. These aren't separate mechanisms, only different loading patterns. A manual-only command sets a disable model invocation flag, so Claude won't fire it on its own, which fits a shortcut you want triggered by hand. A skill can also load itself when its description matches. A sub-agent is a delegated autonomous worker with its own context and tools, an active process rather than a passive template. Skills occupy a specific position in the instruction stack.

**[01:22]** At the bottom, claude.md holds always applied facts and rules that Claude sees on every interaction. No matching or invocation involved. In the middle, skills are description-gated procedures. Claude reads each skill's description and pulls the skill in only when it's relevant to what you asked. At the top, sub-agents are autonomous workers. You spin up when a task should be completed independently.

**[01:50]** Choosing the right layer prevents over-engineering. A simple always-on rule buried in a skill adds complexity for nothing, and a frequently needed team pattern marked manual-only means everyone has to remember to invoke it by hand. Match the mechanism to how it should load. Four patterns tell you a skill is the right choice. Recurring multi-step workflows that you run across many sessions or across a team benefit from being captured once in skill.md rather than redescribed each time. Team-wide conventions that should apply consistently for every contributor belong in a shared skill, not in each person's individual claude.md.

**[02:35]** Procedures that should load automatically when relevant, not on a typed command, fit the way skills get matched by their description. And reusable instruction packages that should run the same way every time benefit from the structure a skill.md gives you. If your workflow fits two or more of these patterns, it belongs in a skill. Knowing when not to build a skill is just as important. One-time tasks don't justify the overhead of writing a formal skill.md. Skills exist for reuse.

**[03:09]** A task you'll run once is better handled in line. Simple lookups don't need a separate skill at all. A claude.md note or a quick slash command is less friction for straightforward requests, and some patterns are better handled by a claude.md rule that's always on rather than a skill that only loads when it matches a request. If the instruction should apply everywhere unconditionally, claude.md is the right place. Skills add complexity. Only build one when the complexity is justified by real reuse value.

**[03:45]** The build decision framework comes down to three factors, frequency, complexity, and reusability. Frequency asks how often this workflow appears across sessions or team members. If it's rare, a formal skill may not be worth the investment. Complexity asks whether the workflow is multi-step enough that a reusable template provides meaningful value over describing it in line. Simple one-liners don't justify the overhead. Reusability asks whether more than one person, session, or team context will benefit from the skill running consistently.

**[04:19]** A workflow that scores high on all three is a strong skill candidate. One that scores low on even one factor should make you consider whether a slash command or a claude.md rule handles it better with less friction. Skills and subagents are both powerful, but they solve different problems. A skill is a passive instruction package stored in skill.md. When its description matches the request, Claude code loads it and follows the instructions itself. The skill is the recipe.

**[04:51]** Claude code is the cook. A subagent is an active autonomous worker you delegate a task to. It has its own context window, tools, and scope. It runs independently and reports back when done. You'll run into scenarios where you have to choose between these two. The key question is whether you need an instruction package that loads when it matches a request, or whether you need a worker to handle something autonomously in parallel.

**[05:19]** Packages versus workers. Skills versus subagents. Skills are worth reaching for when a procedure should show up on its own at the moment it fits, without anyone having to remember to ask for it. That is the whole value of a description-gated middle layer. And it's why frequency, complexity, and reusability are the questions to ask before you write a skill. If a workflow only comes up once, or if it should apply unconditionally everywhere, a simpler mechanism might serve you better.

## 75. Creating and Configuring Custom Subagents

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 75/136 · en_US · auto caption

**[00:00]** Cloud Code can spawn a separate agent instance to take on a piece of work on its own. This lesson covers creating and configuring those subagents. We'll look at what a subagent actually is, how you can spawn one, how context isolation works, how to scope its tools and permissions, and when spawning is the right architecture call. Let's jump in. A subagent isn't another chat window. It's a separate agent instance spawned by a parent through the agent tool inside the same Cloud Code session and handed one delegated subtask.

**[00:34]** It runs in its own isolated context window and reports its results back. Context isolation is the part people underestimate. Each subagent starts fresh with an empty context window, and nothing passes from the parent automatically. Every piece of information the subagent needs has to be included in the handoff. The orchestrator is the parent that decomposes the goal, delegates the work, and synthesizes what comes back. It doesn't share its context window with anything it spawns.

**[01:06]** Subagent, context isolation, and orchestrator carry the rest of this lesson. Cloud Code subagents are different from multi-agent patterns you'd build directly with the API. In the API context, a multi-agent system is usually a set of API completions, you're orchestrating yourself in application code. Cloud Code subagents are separate agent instances inside one session. They're not API calls you're managing. They're spawned via the agent tool within the same session, each running with its own isolated context window and its own configured tools and permissions.

**[01:43]** This distinction matters. Subagents in Cloud Code aren't the same thing as agent orchestration using the API. They operate at a different level and have different characteristics around context, isolation, and tool access. Two paths exist for creating a subagent. The first is a markdown definition file. Custom subagents are defined as markdown files, either in a .cloudagents folder in your project or a .cloudagents folder in your home directory.

**[02:14]** You create one by asking Cloud to write the file for you, or by editing it directly to define the subagents, identity, tools, and scope. The agent tool is the programmatic path. When a parent agent is running an agentic workflow, it can invoke the agent tool to spawn a subagent dynamically as part of that workflow. This is how delegation happens in code. The markdown file gives you a named reusable subagent definition. The agent tool is how subagents get spawned during execution of a larger workflow.

**[02:47]** Four things get configured on a per subagent basis. Tool access controls which tools the subagent can invoke. Bash, file reads, file writes, web access, or others. Isolation is the next lever. A work tree gives the subagent its own copy of the repository to work in, and permission rules scope how far it can reach on the file system. Permissions control what the subagent is allowed to do within its configured scope.

**[03:15]** Subagents can have narrower permissions than the parent. The task description is the explicit set of instructions defining what the subagent should do. All four of these are intentional design choices. You're not just spawning a session, you're defining a scoped permissioned agent with a specific job. Context isolation is one of the most important things to internalize about subagents. When a subagent is spawned, it starts fresh.

**[03:42]** There's no automatic inheritance. The parent's conversation history, already read files, and prior work don't carry over. If the subagent needs information from the parent's session, the parent has to explicitly include it in the handoff instructions. The subagent's results are returned to the parent, which then synthesizes them. Isolation is actually a feature here. It prevents the subagent from being influenced by context that isn't relevant to its task.

**[04:10]** It keeps the subagent focused, but it means the handoff has to be deliberate and complete. By default, a subagent inherits the parent's tools and permission context, but you can configure it with a narrower set than the parent holds. A subagent that's inspecting files can be configured as read-only, meaning it can look but not write. A subagent working on a specific service can be scoped to that directory only with no access to adjacent paths. Restricting tool access reduces the blast radius if the subagent does something unexpected. This is the principle of least privilege applied at the subagent level.

**[04:51]** Give the subagent exactly the access it needs for its task, and nothing beyond that. Restricting below the parent is the intentional opt-in step. Knowing when to spawn a subagent and when to stay in line is a practical design decision. Subagents make sense when tasks are truly independent and can run in parallel. When a task needs a different tool set than the parent is using, or when scope isolation prevents context contamination between separate work streams. Staying in line makes sense when the task needs full parent context to complete, when the work is sequential and depends on prior steps in the same session, or when the task is simple enough that delegation overhead exceeds the value.

**[05:35]** The overhead of spawning a subagent is real. Don't spawn one unless the isolation or parallelism actually buys you something. The handoff is a design artifact, not an afterthought. When you spawn a subagent, you're writing the only instructions it will ever have. There's no shared context. There's no ability to ask a follow-up question from the parent mid-task.

**[05:59]** The handoff needs to include a precise task description, defining what done looks like, the necessary context, only what the subagent actually needs, and the output format, exactly what structure you expect the subagent to return. If any of these three are underspecified, the results will be ambiguous or unusable. Designing the handoff is the most important part of deploying a subagent effectively. People hear isolated and they picture complete isolation. That's not quite what we're talking about here. Context is walled off, so the parent's conversation and open files don't carry over.

**[06:38]** But tools and permissions come down from the parent unless you narrow them yourself. Those are separate dials. Once you see them as separate, the choice of what to configure on each one stops feeling arbitrary. That brings this one to a close. I'll see you in the next video.

## 76. Designing Subagents for Delegation

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 76/136 · en_US · auto caption

**[00:00]** If you're spawning subagents and getting back results you can't use, the problem is almost always in the design, not the execution. In this lesson, we'll look at the three design questions every subagent needs. Context window allocation. The built-in subagents you get out of the box. Structured output design. Error reporting.

**[00:19]** And the anti-patterns that make delegation counterproductive. Most disappointing subagent results trace back to a design decision, not a bug. The three design questions are what task, what context, and what output format. And every effective subagent gets all of them answered before anything is spawned. Structured output means the subagent returns parsable, well-formed results, rather than a natural language summary. Because the parent needs to process results, not interpret them.

**[00:52]** Delegation overhead is the real cost of spawning and managing a subagent. Context loading, coordination, latency, and cost all count. And for a simple task that overhead can exceed the benefit. Knowing where that line sits is the design skill this lesson builds. Before spawning any subagent, answer three questions. What task?

**[01:15]** Precisely what should this subagent do? And what does done actually look like? What context? Exactly what information does the subagent need to complete that task? Not what might be useful. Not everything the parent knows.

**[01:29]** Exactly what this specific task requires. And what output format? How should the results be structured so the parent can actually use them? If you skip any of the three, you've built an underspecified subagent. It might run. It'll return something.

**[01:45]** But the results will be inconsistent, hard to process, or simply wrong because the design was incomplete to begin with. These three questions are the minimum viable design checklist. Context window space in a subagent is a finite resource. The same as anywhere else. The difference is that the subagent's context is entirely provided by the parent. There's no background knowledge being drawn from a shared session.

**[02:12]** What you pass is what the subagent has. More context isn't better if it's not relevant to the task. Overstuffing the context window with everything the parent knows crowds out the task-relevant content and makes the subagent less focused. The parent holds the full context. The subagent needs a focused, purposeful slice of it. Disciplined context allocation keeps the subagent efficient, keeps costs lower, and produces better results because the subagent isn't filtering through irrelevant noise.

**[02:48]** Before you hand-build every subagent, know that Clawed Code ships with a few ready-made ones. Explore is built to investigate. It reads through the codebase and reports back what it found without making edits, which is exactly what you want during the research phase. Plan is a read-only research agent that gathers codebase context in plan mode. It doesn't draft the approach itself. It hands its findings back, and the main conversation presents the plan.

**[03:17]** General purpose handles open-ended tasks that don't fit a narrower role. What ties them together is that delegation is description-driven. You describe the task clearly, and that description routes the work to the right subagent. One more knob worth knowing. You can route each subagent to its own model. Matching model capability to task cost is how you keep a multi-agent workflow both effective and affordable.

**[03:45]** Structured output is a design requirement, not a nice-to-have. When you define a subagent's task, you also define exactly what it should return. That means specifying a schema, JSON fields, YAML structure, or named output sections. The subagent should return a success or failure indicator as part of that output, so the parent can check it programmatically. Results should be machine-parsable, not natural language descriptions. A summary written in prose might be readable by a human, but it can't be reliably parsed by the orchestrating parent agent.

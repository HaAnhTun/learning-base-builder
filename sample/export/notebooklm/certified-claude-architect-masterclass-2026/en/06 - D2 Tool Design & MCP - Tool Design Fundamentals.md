## 33. Writing Tool Descriptions That Route Correctly

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 33/136 · en_US · auto caption

**[00:00]** Knowing that Claude routes on descriptions is the foundation of tool selection. Writing a description that actually works across varied inputs, handles ambiguous cases, and holds up under real-world agent traffic is the craft. That's what this lesson is about. These ideas frame everything we'll do from here related to tool use. A strong tool description has three required components. First is what it does, a clear purpose statement covering the tool's function and its return value.

**[00:32]** Second is when to use it, the explicit conditions that should trigger selection. Third is when not to use it, the exclusion clause that tells Claude what falls out of scope. Anthropic recommends at least three to four sentences per description, and more when the tool is complex, because that is usually what it takes to cover all three parts well. The third component is the one most commonly skipped, and it is often the direct reason for misrouting when tools share a similar function. Leave any component out, and you have opened a routing gap that surfaces when your agent is handling real traffic. Your description should also signal what kinds of inputs the tool expects.

**[01:14]** This doesn't mean pasting the JSON schema into the description. It means summarizing the input intent. If the tool takes a customer ID and a date range, say so. If it expects a query string, say that. If the input needs to be a valid enum value, name the constraint. These input hints in the description help Claude form the call correctly, not just select the right tool.

**[01:38]** There's a meaningful difference between those two outcomes. One gets you the right tool, the other gets you a correct tool invocation with well-formed arguments. Output format is equally important and equally skipped. When Claude selects a tool, it's implicitly asking whether calling this tool will produce what the request needs. If the description doesn't say what the tool returns, Claude can't answer that question with confidence. Tell it whether you're returning a single object, a list, a Boolean, or a status code.

**[02:10]** Note whether the output is ready to use or requires transformation. Flag how errors surface. Does the tool return null, raise an exception, or include an error field in the response? Output framing completes the picture Claude needs to select and use a tool correctly. When your tool surface grows, three strategies keep selection unambiguous, and the first two come straight from Anthropic's own guidance. The first is consolidation.

**[02:38]** Rather than a separate tool for every action, like create, review, and merge, group the related operations into one tool with an action parameter. Fewer, more capable tools mean less for Claude to disambiguate. The second is namespacing. When tools span multiple services, prefix each name with its service, like github underscore listprs or slack underscore sendmessage, so the owning service is obvious from the name alone. The third is explicit exclusion. State what a tool doesn't handle, such as it doesn't do bulk updates or deletions.

**[03:14]** Together, these shrink the space Claude has to reason over, and make the right tool the obvious one. Let's look at what happens when two tools have overlapping, vague descriptions, versus when they're cleanly separated. With overlap, Claude has no confident basis for selection. It might call either tool, and the routing is essentially unpredictable, across varied input phrasings. With clean separation of domain anchors, trigger conditions, and exclusion clauses, Claude selects the right tool consistently. The descriptions did the disambiguation work up front, so Claude doesn't have to guess at runtime.

**[03:52]** That's the standard you're aiming for. You want descriptions so precise and well-bounded that correct selection becomes the reliable outcome, regardless of how the user phrases their request. Writing a good description gets you to step one. Confirming it routes correctly across the real input distribution gets you to step two. And there are three tests worth running before you ship. A positive test sends a request the tool should handle, and confirms both correct selection and correct argument formation.

**[04:23]** A negative test sends a request the tool shouldn't handle, and confirms Claude routes to an alternative, or asks for clarification rather than guessing. A disambiguation test sends a request that plausibly matches more than one tool, and confirms the right one wins on description specificity, not position in the list or name similarity. Run all three before deploying any toolset, and you get evidence-based confidence in routing reliability. In production, this can go wrong quietly. A toolset that routes perfectly with a handful of tools starts picking the wrong one once the catalog grows and users phrase requests that you never predicted. Purpose, trigger conditions, and exclusions keep those boundaries sharp.

**[05:12]** And the positive, negative, and disambiguation tests are how you prove they hold before real traffic finds a gap. That wraps up this one. I'll see you in the next lesson.

## 34. Designing Tool Input Schemas for Precision and Reliability

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 34/136 · en_US · auto caption

**[00:00]** When Claude calls a tool, it generates arguments based entirely on your schema. If the schema is vague, Claude's arguments will be too. A well-designed schema acts like a contract, specifying what to send and in what format. For this video, we'll cover how JSON Schema drives tool input design and why precision is the biggest lever for call reliability. Every argument Claude generates is shaped by what your schema declares, so it's worth knowing exactly what that object contains. A tool schema is the JSON schema object you attach to your tool definition.

**[00:36]** It specifies every accepted parameter, its type, any constraints, and which fields are required. Claude uses this schema to shape the arguments it generates. By default, the schema is best effort guidance. To guarantee arguments conform exactly, you set strict tool use on the definition. A tool input parameter is any named field inside that schema, carrying a value Claude has to supply. Parameters can be required or optional, typed, and described.

**[01:07]** Schema validation is the step where generated arguments are checked against the declared structure. JSON Schema is the standard format for declaring tool inputs in the Anthropic API. It's a machine-readable object that tells Claude which fields exist, what types they accept, and what constraints apply. Here's an important detail. Claude reads your schema at inference time, not just at definition time. That means every property you declare is actively shaping how Claude constructs its arguments right now in this call.

**[01:39]** If you enable strict tool use, the model is held to the grammar-enforced parts of your schema, its types, enums, and required fields, which acts as a safety net at generation time. Length and range bounds stay advisory, so that safety net only helps where your schema uses the constraints that are actually enforced. Parameter names are the first signal Claude uses to understand what a field is for. A field called ID could mean a user ID, an order ID, a product ID, or a session ID, depending on context. A field called customer ID removes that ambiguity completely. The guidance here is straightforward.

**[02:18]** Use specific descriptive names in SnakeCase, avoid abbreviations the model might misinterpret, and make sure the name reflects the domain meaning of the field rather than how you've implemented it internally. This matters because Claude is reading names as semantic signals, not just identifiers. When parameter names are clear, Claude is far less likely to populate them with plausible but wrong values. Naming anti-patterns are worth calling out directly, because they show up all the time in real schemas. Generic names like data, input, or value give Claude no context about the field's purpose, so it's left to infer from surrounding conversation. Overloaded names, where the same field name means different things in different tools, compound the problem because Claude builds up associations over a session that carry over incorrectly.

**[03:14]** Cryptic abbreviations like usractnum or acttpcd force the model to guess at meaning, and increase the risk that it guesses wrong. Each of these patterns produces tool calls that look structurally valid, but carry incorrect content. Here's a design insight that surprises a lot of developers. Parameter descriptions aren't just documentation for humans. Claude reads them at inference time as part of argument generation. A description like the user id technically communicates what kind of data belongs in the field, but a richly specified description tells Claude the source, the expected format, and the constraints all at once.

**[03:56]** The strongest descriptions name the field's purpose, the valid values it accepts, and how it should behave at the edges. Omitting descriptions degrades argument quality even when your types are correct. Think of every description as a mini instruction, written directly to the model, because that's exactly what it is. Let's make the contrast concrete. A weak description says the user id. That's technically accurate, but seriously underspecified.

**[04:24]** Claude knows it's some kind of identifier, but it doesn't know the format, where it comes from, whether it's numeric, or a uuid, or how long it should be. A strong description says uuid of the authenticated user from the session token, formatted as 32 hexadecimal digits, displayed in 5 hyphen separated groups, 36 characters total. That tells Claude the exact format, the source of the value, and the length, all in one sentence. There's no room for misinterpretation. The difference in argument quality between these two descriptions is measurable, especially for identifier fields where the format has to be precisely right, or the call fails. Under strict tool use, JSON schema constraints aren't all enforced the same way.

**[05:12]** Type, enum, and supported format values are grammar-enforced, so Claude can't generate anything outside them. The type property declares whether a field is a string, an integer, a number, a boolean, or an array. The format property adds a semantic layer, hints like date, time, or email, that tell both Claude and your validators what the string represents. Pattern is a regular expression the value has to match, and it's only partially enforced, so check it in your own code. Length and range, bounds like min-length and maximum, are purely advisory, validated after the fact. Lean on the enforced constraints for hard guarantees, and re-validate the advisory ones before the call reaches your backend.

**[05:59]** There's a line worth drawing between the parts of a schema that constrain Claude, and the parts that only persuade it. Types and enums are enforced at generation. Names and descriptions steer, and length bounds get checked after the fact. Once you know which is which, you stop trusting a good description to guarantee everything. The rest you validate in your own code. That's a wrap on this one.

## 35. Required vs. Optional Parameters, Enums, and Constraints

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 35/136 · en_US · auto caption

**[00:00]** Not every parameter carries the same weight. Some fields are essential for the tool to function at all. Others add useful context when it's available. In this video, we'll cover required and optional parameters, how enum fields constrain Claude to a fixed set of values, where input examples help, and how bounds finish a reliable schema. Every field you put in the required array is a promise that Claude can always supply it. So let's lock down three definitions.

**[00:25]** A required parameter is any field listed in that top level required array. Claude has to include it in every call, and if its generated arguments are missing one, the call fails schema validation before your tool code ever runs. An optional parameter is any field not in that array. Claude may omit it when the information isn't available, and your tool code has to be ready for that. A default value is the fallback that applies when an optional parameter is omitted. Defaults can be declared in the schema itself or handled inside the tool implementation.

**[01:06]** Using defaults well is what makes optional parameters safe rather than fragile. Here's a design tension worth understanding. Every field you put in your required array increases the chance that a tool call will fail when Claude is working in a context where that information isn't available. When Claude can't find a value for a required field, it sometimes hallucinates one to satisfy the schema. That's worse than a failed call because the hallucinated value looks valid but isn't. The discipline here is to only mark a field required if the tool genuinely can't function without it.

**[01:43]** If the tool can produce a sensible result with a default or skip the field entirely, make it optional. A simple decision framework helps when you're not sure whether a field should be required or optional. If the tool can't function without it, mark it required and accept that the call should fail fast when the value is missing. If the field is useful but not critical, make it optional and declare a sensible default in your implementation so the tool still produces a good result. If the value is rarely provided, make it optional and handle its absence explicitly in your tool code. This framework keeps your required set lean, which means Claude can call your tool successfully across a wider range of contexts without resorting to hallucination.

**[02:30]** When a parameter accepts only a fixed set of values, an enum constraint is exactly the right tool. You declare enum as an array of the acceptable values for that field, and Claude picks from that list instead of generating a free-form string. Under strict tool use, the model is guaranteed to stay inside the set. That's especially powerful for routing parameters like a priority field that sends requests to different handlers. A couple of related constraints round this out. Minimum and maximum apply numeric bounds to integer and number fields, which matters for page sizes, scores, and item counts, where an out-of-range value breaks something downstream.

**[03:14]** And additional properties set to false declares that no undeclared fields are allowed, which strict tool use enforces so Claude can't invent extras. The contrast between a free-form string and an enum field makes the value concrete. Without an enum, a priority field declared as type string gives Claude unlimited options. It might generate urgent, high priority, urgent, critical, or any other variation depending on whatever context happens to be in the conversation at that moment. All of those variations may break the logic that branches on the value because your code is almost certainly checking for exact string matches. Add enum, low, medium, high, and Claude has to pick one of those three exact values every single time, regardless of context.

**[04:04]** The field becomes deterministic and predictable. Your back-end code gets simpler and more reliable as a direct result of that single schema change. Enum fields show up in two main patterns in real-world tool schemas. The first is routing inputs, where the enum value directs the tool call to a specific handler, workflow, or service. The second is extraction fields, where Claude is classifying an entity or event into a predefined category, like a sentiment label or a document type. In both cases, the valid set has to be stable and reasonably small.

**[04:42]** Enums work well for two to ten values that don't change often. If your valid set has hundreds of members or changes frequently, enum isn't the right constraint and you'll want a different validation approach. Constraints tighten what Claude can generate, but sometimes a valid shape still isn't an obvious usage pattern. That's what the input examples field is for. You add an optional input examples array to the tool definition, holding a few sample inputs, and each one has to be valid against your input schema or the whole request is rejected. Descriptions are still the most important lever, so reach for examples when a tool has nested objects, a lot of optional fields, or format-sensitive parameters where valid JSON doesn't guarantee correct usage.

**[05:32]** Examples measurably improve accuracy on complex parameter handling. They cost a few extra prompt tokens and they aren't supported on server tools, but on genuinely complex tools, they earn their place in the definition.

**[05:50]** Let's pull this together. Only mark fields required when the tool genuinely can't function without them. Give optional fields sensible defaults and use enum constraints to eliminate freeform string variation for any fixed value input. Numeric bounds and additional properties tighten the rest. Those decisions are what separate a schema that Claude can satisfy every time from one that quietly produces bad calls. That's it for this lesson.

## 36. Strict Tool Use and Valid Inputs

**[00:00]** Hello. Forcing a model to call a tool only gets you halfway. The call still has to carry the right inputs, in the right types, with nothing missing. In this lesson, we'll go through strict tool use, a single setting that guarantees the model's tool inputs match the schema you defined. Let's get into it. Let's start with the pain it removes.

**[00:23]** Without strict mode, the model can hand your function the wrong shape of data. Say your schema expects a number of passengers. You might get back the word two spelled out as a string. Or you might get a two wrapped in quotes, which is a string, not the integer your code wants. Worse, the model might leave out a field you marked as required entirely. Every one of those breaks the function you're trying to call.

**[00:46]** And the usual fix is ugly. You write code that inspects the tool call, checks whether the types are right, and if they're not, you re-prompt the model and hope the second try is cleaner. That validate and retry dance is exactly what strict mode is designed to end. So, what does strict actually promise you? Three things. First, a valid name.

**[01:01]** The tool name the model returns is always a real tool from your request. It can't invent one that doesn't exist. Second, no type mismatch. Every argument matches the type your schema declared. If you said integer, you get an integer. Never a string standing in for one.

**[01:26]** Third, no missing fields. Every required field is present. Nothing your function depends on quietly goes missing. Put those together and you have a hard guarantee. The tool call conforms to your input schema every time by construction. You're not hoping the model got it right.

**[01:44]** The system makes it impossible for the call to come out any other way. Now, let's look under the hood because the how is genuinely clever. You enable it by adding one property to your tool. You set strict to true right alongside the name, the description, and the input schema. Every object in your schema also needs additional properties set to false, and leaving that out gets you a 400 from the API. When you do that, the API takes your schema and compiles it into a grammar.

**[02:14]** That grammar then constrains the model's token sampling as it writes the tool call. At every step, the model can only produce tokens that keep the output valid against your schema. Anything that would violate it simply can't be sampled. It's called constrained decoding, and it happens live as the model generates, not as a check afterward. Here's my favorite part. What you get to stop writing.

**[02:38]** Because the guarantee holds by construction, you get no validation layer. That's the code that used to inspect every tool call and confirm the types and fields were correct. Gone. You also get no retry loop, the logic that re-prompted the model whenever a call came back malformed. Also gone. What's left gives you type safe calls.

**[03:02]** Your functions receive correctly typed arguments every single time, which means they behave predictably even when you're running at real production scale. Less code, fewer failure paths, more confidence. That's a genuinely good trade, and it's the practical reason Teams turns strict on for agent work. Now I want to draw a clear line between two features that sound similar, because students mix them up constantly. Strict tool use constrains the tool inputs. It makes sure the arguments going into your functions conform to your input schema.

**[03:30]** It's about what flows into the tools. Structured outputs, on the other hand, constrains the text response itself. It shapes the model's final answer to a schema you provide. It's about the shape of what comes back to the user or the calling code. Same underlying idea, valid by construction, pointed at two different targets. One governs the tool call inputs, the other governs the response.

**[04:00]** Keep that distinction sharp and you'll always know which one you actually need. Here's what ties them together under the surface. Strict tool use compiles your schemas into grammars using the very same pipeline that structured outputs uses. It's not a separate system bolted on, it's the same machinery aimed at tool inputs. Because of that shared foundation, both features accept the same supported subset of JSON schema. That matters in practice.

**[04:24]** A handful of the more advanced schema keywords aren't allowed, so you keep your schemas within the supported subset. And there's a performance nicety. Those compiled schemas get cached for up to 24 hours since their last use. So if you call the same tool repeatedly, you skip the recompilation cost after the first time. Same pipeline, same schema rules, same cache. One more thing worth calling out because it connects straight back to how you steer tool selection.

**[04:55]** Strict combines cleanly with the tool choice settings we looked at earlier. Set tool choice to any and you guarantee that some tool gets called. You're certain a call happens and you're certain the call is well formed. There's no gap left where the model could either skip the tool or feed it garbage.

**[05:23]** For anyone building agent workflows that have to run unattended, that combination is a genuinely strong foundation to build on. Reliable trigger, reliable payload. ## 37. Returning Useful Errors from Tools

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 37/136 · en_US · auto caption

**[00:00]** When a tool breaks, what it sends back matters as much as what it does when it works. Claude reads that response to decide whether to retry, ask you directly, or try something else. In this video, we'll design tool errors that carry real information, and cover why anything a tool returns deserves a measure of suspicion. A tool that fails and returns the word error has told Claude almost nothing. A tool error response is a structured reply that says execution failed and explains why, carrying an error type, a human-readable message, and optional metadata Claude can reason over. That structure is what turns a dead end into an actionable signal.

**[00:44]** Inside it, the error code is a short, stable string that code and models can act on without reading the message text. The suggested action tells Claude what to do next, whether that's retry, ask the user, or escalate. Together, these pieces give Claude a complete picture of what went wrong and how to respond. It helps to know what the tool result block actually looks like when Claude sends it back, because it's leaner than people expect. It carries just three fields. The tool use ID matches the result back to the specific call Claude made.

**[01:20]** The content field holds the result itself, and when the tool fails, that same field holds your error message. And the is error flag set to true tells Claude the execution failed rather than succeeded. There's no dedicated error code field, no separate context field, nothing else in the block. So any richer error, shape you design, a code, a reason, a suggested action lives inside the content field as text. Claude reads it there. Keep that in mind.

**[01:45]** The structure you invent is a convention inside content, not extra fields on the block itself. One of the most useful distinctions in error handling is whether the failure is a user error or a system error. User errors mean the caller sent bad data, the wrong format, a missing required field, or a value that's out of range. For these, retrying won't help. Claude should surface the problem to the user and ask for a correction. System errors are different.

**[02:15]** A timeout, a service that's temporarily unavailable, or an unexpected upstream response are all things the user didn't cause and can't fix. For these, Claude can retry, wait, or try an alternative path without involving the user at all. Your error code should make this distinction explicit. When you write error messages, keep in mind that Claude is the primary consumer, not a developer reading logs. Codes need to stay stable across versions, so any routing logic built on them doesn't break when you ship an update. Include the input value that triggered the error in the context field, because the same code can mean different things depending on which parameter failed.

**[02:58]** And avoid raw stack traces as the main message. A stack trace is useful in a log file, but it's noise in a tool response. Replace it with a clean message and put the technical details somewhere else. The goal is an error that Claude can act on, not just read. These four fields form the skeleton of a well-designed error response. The error code is the stable, machine-readable string that never changes across versions.

**[03:29]** The message is the human-readable description you'd be comfortable surfacing directly in a chat reply without editing. The context block carries the key value pairs that identify what failed and why, so debugging doesn't require guessing. And the suggested action is the explicit hint about what Claude should do next, which saves it from having to infer the right path on its own. Each field serves a different consumer. The code serves routing logic. The message serves users.

**[03:59]** The context serves debugging. The suggested action serves Claude's decision engine. Design each one with its consumer in mind. The suggested action field is optional but valuable, because it points Claude toward either recovery or escalation. Recovery means Claude handles the problem on its own. It tries again with a different value, reformats its input, or switches to an alternative tool.

**[04:24]** Escalation means Claude brings a human into the loop. Because the problem needs judgment, the model can't provide. A rate-limited error should say to retry after a short delay. An incorrect input error should say to ask the user to correct the value. A service-unavailable error might say to try an alternative tool or escalate. Error routing is what ties this together, using the error code to pick the right path automatically.

**[04:50]** A well-designed set of codes lets you define those routing rules once and apply them across every tool you own. A few mistakes show up repeatedly in tool error design. The first is returning a success status with an error buried somewhere in the response body. Claude may not look for it, and the model will proceed as if the call succeeded. The second is using vague codes like failed or error with no subtype, which forces Claude to parse the message to understand what happened. The third is leaving out context, when the same code can mean different things depending on which input failed.

**[05:26]** Each of these mistakes adds friction to recovery and increases the chance that Claude makes the wrong next move. Specific, context-rich errors are worth the extra effort. There's one more thing to internalize, and it's a security point, not a formatting one. A tool result often carries content from sources you don't control. A fetched web page, an inbound email, a user upload, a third-party service response. You have to treat all of that as untrusted input.

**[05:56]** An attacker who can influence it may bury instructions in the text that try to redirect Claude, telling it to ignore its task or leak data. That's indirect prompt injection, and it turns your tool into a confused deputy acting on someone else's orders. The guardrail Anthropic recommends is to keep that untrusted content inside tool result blocks. Never promote it into the system prompt or a plain user message, so the model always knows it came from a tool and treats it with appropriate suspicion. Here's the big picture. ## 38. Tool Retry Logic and Partial Success Patterns

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 38/136 · en_US · auto caption

**[00:00]** Tool failures don't always mean the operation is impossible. Sometimes a service is temporarily overloaded, or a retry will succeed. Sometimes a batch job finishes half its items before hitting an error. In this video, we'll work through retry-safe patterns, partial success responses, and circuit breakers for unreliable downstream services. Let's get into it. A retry sounds harmless until it charges a customer twice.

**[00:27]** Partial success describes the outcome when a batch tool completes some operations and fails on others. The response has to say which items succeeded and which didn't, so Claude can reason about what to do next. Idempotency is the property that calling a tool twice with the same input is safe. It's the foundation of retry logic, because without it, retrying a call can create duplicate side effects. And the circuit breaker is a pattern that cuts off calls to a failing downstream service after repeated failures, preventing the kind of cascading errors that fill a context window with noise. Before you retry, you need to know whether retrying actually makes sense.

**[01:12]** Transient errors like timeouts and rate limit responses are the clearest candidates. The service was busy or temporarily unavailable, and waiting a short moment before trying again is the right call. User errors are the opposite. If the input was invalid, sending the exact same request again won't fix anything. Claude should surface the problem to the user and ask for a correction instead. System errors without a suggested action fall somewhere in between and need judgment before retrying.

**[01:44]** Your error codes should make the category explicit, so Claude doesn't have to infer it from message text alone. Idempotency is the key property that makes retry safe. An idempotent tool returns the same result whether you call it once or ten times with the same input. A lookup or a read is idempotent by nature. A write that creates a new record isn't, unless you build idempotency indeliberately. The standard pattern is for the caller to generate a unique idempotency key and include it with the request.

**[02:17]** The tool stores the key, and if it sees the same key again, returns the original response instead of executing again. Payment APIs use this pattern extensively. It's worth adopting in any tool that creates or modifies state. Designing for safe retry starts at the tool interface level. The most direct approach is accepting a caller-provided idempotency key with every state-changing request. The tool stores the key alongside the result and returns the cached result for any duplicate call.

**[02:48]** Conditional writes are another option. The tool checks current state before applying a change and skips the write if it's already been applied. Either approach turns a non-idempotent operation into one Claude can safely retry on transient failures. The cost is a bit of storage and a lookup on each call. The benefit is that Claude never creates a duplicate charge, email, or record because of a network hiccup between the tool call and the response. Three retry failure modes come up frequently enough to call out by name.

**[03:23]** Duplicate side effects happen when a non-idempotent tool gets retried and creates two records, charges, or messages instead of one. This is the most expensive failure mode because real-world consequences like double charges are hard to reverse. Infinite retry loops happen when there's no back-off delay or retry limit, so Claude keeps hammering a failing service until the context window fills. And stale state failures happen when a retry reapplies steps that already completed during a partial run, leaving the system in an inconsistent state. Each of these is avoidable with the right design choices. Idempotency keys prevent duplicates.

**[04:02]** Back-off and limits prevent loops. And partial success responses prevent rerunning completed steps. Partial success is the case where a batch tool completes some items and fails on others. The wrong response is to return a generic error that hides what succeeded. The right response uses a partial success status and splits the result into two lists. A succeeded list with the IDs or keys that completed, and a failed list with per-item error codes and context.

**[04:33]** When Claude receives this structure, it can decide what to retry, what to skip, and what to surface to the user. Without it, Claude either has to guess or rerun the entire batch, which risks duplicating the operations that already finished. Surfacing partial success explicitly is what the Architect Foundation's exam tests in this area. The circuit breaker pattern manages the relationship between your tool and an unreliable downstream service. It has three states. In the closed state, calls pass through normally and failures are counted.

**[05:08]** Once failures exceed a threshold, the breaker opens and calls are blocked immediately without hitting the downstream service. After a configured interval, the breaker moves to half open and allows a single probe call through. If the probe succeeds, the breaker closes and normal traffic resumes. If it fails, the breaker stays open and the interval resets. This pattern prevents Claude from filling its context with errors while waiting for a service that won't recover on its own. You should add a circuit breaker when a downstream tool has intermittent outages that aren't predictable.

**[05:44]** The configuration has three parameters you need to set deliberately. The failure threshold is how many consecutive failures trigger the open state. Set it too low and the breaker trips on normal variance. Set it too high and you waste calls on a broken service. The recovery probe interval is how long to wait before testing the service again. And the fallback defines what to return while the circuit is open.

**[06:09]** A cached result, a simplified response, or a clean error that tells Claude to escalate. Without a fallback, the circuit breaker just converts tool failures into blocked calls. The types of failures that nobody forgets are things like a retry that charged a customer twice or the batch that resent every email because the response only said error. Reliability lives on the tool side. An idempotency key makes a repeat call harmless. A succeeded and failed split tells Claude exactly what's left.

**[06:46]** And a breaker keeps it from hammering a service that's already down. That's a wrap on this one. I'll see you in the next lesson.

## 40. Selection Heuristics and Tool-Selection Failures

When routing goes wrong, it fails in recognizable patterns, and naming them is what makes them fixable. A no good match failure happens when none of the available tool descriptions closely match the user's request. The model might fabricate a tool name, refuse to act, or call the least wrong option, and silently produce bad output. Those silent errors are the hardest ones to catch.

**[00:41]** A two good matches failure happens when two tools both look like valid candidates. Disambiguation patterns are the description writing techniques that make each tool the unambiguous winner for its intended request type. On every turn, the model reads the incoming request and scores each available tool's description for relevance.

**[01:23]** The highest scoring match wins, and the model calls that tool. Notice what's not in this process. The model doesn't run the tool and check whether the output looks right. A tool that can do exactly what the user needs will still lose out at selection time if its description is vague, generic, or uses vocabulary that doesn't align with how users phrase their requests.

**[01:54]** Writing descriptions is a form of precision engineering, not documentation. The most reliable fix for both failure modes is writing descriptions that make each tool the unambiguous winner for its intended request type. The two core techniques are distinct verbs and narrow scopes. Distinct verbs means each tool description starts with a verb that doesn't apply to any other tool in the palette. Retrieves, writes, deletes, summarizes, translates. These verbs signal intent clearly and rarely overlap.

**[02:27]** Narrow scope means you tell the model not just what the tool does, but what it doesn't do. Retrieves records from the user database, doesn't write or update records. That negative boundary is often more useful than the positive description because it's exactly what the model needs to break a tie between two similar tools. One effective pattern is adding an explicit routing section to the system prompt. This section names each tool and states when to use it versus the alternatives.

**[03:12]** It's particularly useful when you have tools that are similar by nature and can't be distinguished by description alone. Tie-breaking instructions are another technique. For example, prefer the cached retrieval tool when the data is less than five minutes old. Negative examples round out the toolkit. **[03:48]** Routing quality doesn't stay constant. As you add tools, rename them or adjust descriptions. Selection behavior changes, and users change how they phrase requests over time too. **[04:07]** Log every tool call with the tool name and the request that triggered it. Over time, you can track selection frequency for each tool. **[04:37]** One of the most common mistakes teams make when a tool isn't being selected correctly is adding a new tool to cover the gap. That's almost always the wrong move. Adding a tool grows the catalog, which increases context overhead and introduces new opportunities for overlap. A better description fixes the selection problem without any of the downsides.

**[05:06]** The rule I'd suggest is to default to refinement and add a tool only when the use case is genuinely outside the scope of anything you already have. The model reads the request, ranks each description for fit, and calls the winner. Routing accuracy is therefore something you engineer in the wording, mostly with distinct verbs and an honest boundary on what a tool won't touch.

## 44. Tools, Resources, and Prompts — The Three MCP Primitives

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 44/136 · en_US · auto caption

**[00:00]** MCP exposes capabilities through exactly three primitives, tools, resources, and prompts. Once you understand each one and who controls it, you know how to model any capability on an MCP server. In this lesson, we'll define each primitive, see what makes them different, and build intuition for which one to use when. Every capability an MCP server exposes is a tool, a resource, or a prompt. And what separates them isn't what they do, but who decides to use them. An MCP tool is a callable function the model invokes.

**[00:33]** An MCP resource is a data object identified by URI, which the application injects into context. An MCP prompt is a reusable, parameterized template the user selects to start an interaction. Notice the pattern, each primitive has a different owner. That ownership distinction is the single most important thing to internalize here, and it's a concept the Architect Foundation's exam tests directly. Model controls tools, application controls resources, user controls prompts. Memorize that split and you've got the core of the primitives topic locked down.

**[01:11]** Tools are the most active primitive. When you expose a function as an MCP tool, you're giving the model the ability to do something, such as run a database query, send a notification, call a calculation service, or trigger any other side-affecting operation. Each tool gets a JSON schema that describes its name, required inputs, types, and what it returns. Claude reads that schema and uses it to understand how to invoke the tool correctly. Then it reasons about whether calling the tool actually serves the user's goal in this conversation. The key word is decides.

**[01:47]** The model is in control of when and whether the tool gets called. That's the practical meaning of model controlled. Resources work differently from tools. They're data sources that the server exposes for the model to read. Files, database records, configuration documents, and knowledge bases. The application injects them into Claude's context before or during a conversation.

**[02:12]** The server registers each resource with a URI so clients can address and request it. But the decision about which resources to include in context isn't made by the model. The host application makes that call based on its own logic about what data should be present. So if you've got a knowledge base that should always be in context when a user asks a product question, that's a resource. The app loads it automatically, not because Claude asked for it. The comparison between tools and resources comes down to control and dynamism.

**[02:48]** Tools are model controlled and action oriented. Claude uses them when the conversation warrants it based on its own in-context reasoning. Resources are application controlled and data oriented. The host loads them based on its own business logic, completely independent of what the model thinks it needs. Here's a practical heuristic. A weather lookup the model calls on demand because the user asked about the weather.

**[03:18]** That's a tool. A company policy document, the application always loads into context before any compliance related conversation. That's a resource. When you're designing a server, just ask yourself, who makes the decision to use this, the model, or the application? The ownership model is worth sitting with a bit longer because the three-way split isn't arbitrary. It's principled.

**[03:43]** The model controls tools because it's the one reasoning about what action needs to happen next in a conversation, and it has the most context for that decision. The application controls resources because it has the broader system level context to know what data should be present for a given workflow or user state. The user controls prompts because prompts are really about letting humans configure their own starting point intentionally before an interaction begins. MCP landed on this split deliberately. Each ownership model maps to the party with the most relevant information to make that specific decision correctly, safely, and without overstepping. Prompts are the third primitive.

**[04:28]** They're reusable, parameterized templates stored on the server that users can browse and explicitly apply. Think of them as pre-built workflows a user can launch by name. The mental model, a user opens a chat interface, sees a list of prompts the connected server makes available, picks one, fills in any required variables, and the interaction starts with that template already applied and active. The user is explicitly initiating this. The model doesn't choose to apply a prompt on its own, and the application doesn't inject it silently without the user knowing. The human makes a deliberate, intentional selection.

**[05:04]** That's the practical meaning of user-controlled for this particular primitive. When you're designing an MCP server, the primitive choice is a real design decision with real consequences for how your server gets used and misused. Use a tool for actions or computations the model should trigger during its reasoning, such as search queries, calculations, and mutation operations that change state. Use a resource for background data the application should load and inject before the model generates a response. Use a prompt for reusable starting point workflows that make sense for users to select intentionally before beginning a task. The reliable shortcut is always to ask who drives this decision.

**[05:46]** If it's the model, it's a tool. If it's the application, it's a resource. If it's the user, it's a prompt.

**[06:00]** People tend to lump tools and resources together because both end up as information that the model uses. The real split is who pulls the trigger. Claude reaches for a tool because the conversation calls for it. Your application pushes a resource in because its own logic says to do so. Once you sort capabilities by who decides rather than by what comes back, server design stops being guesswork. That wraps up this lesson.

The SDK supports both transports with the same tool registration API. Every MCP server follows the same three-part structure. You create an instance of the MCP server class and give it a name.

**[03:06]** You register tools, resources, and prompts on that instance using decorators. Then you call run with your transport and the server blocks, processing requests until it shuts down or crashes. Run wraps a syncio under the hood, so you never manage the event loop yourself. Version 2 of the SDK renamed this class from FastMCP, and the old import path is gone, so upgrading breaks any project that still reaches for the old name. There is also a lower level server class, but it takes its handlers as constructor arguments instead of decorators, so the two aren't interchangeable. Everything ahead builds on the MCP server class.

**[03:50]** A recommended project layout separates concerns into four files. The server.py entry point creates the MCP server instance and calls run. A tools.py module holds all tool definitions and handler functions imported at startup. A requirements dot txt pins MCP and any tool dependencies, so deployments are reproducible across machines and environments. A readme documents the transport, available tools, and any environment variables the server requires to start. This structure keeps the entry point readable and makes it easy to add new tools without touching the startup logic.

**[04:29]** As your server grows, you can split tools.py into domain-specific modules without changing how the server itself is initialized or started. The MCP server class manages startup and shutdown through a single lifespan async context manager, not separate hooks. You write an async function decorated with async context manager and pass it to the constructor. Everything before the yield statement runs once at startup, so that's where you open database connections, load configuration, and warm any caches your tools need. The yield hands control to the running server. When the server shuts down, execution resumes after the yield, and a finally block is where you close connections, flush buffers, and release file handles cleanly.

**[05:13]** Because it's async, you can await inside it. Your handlers reach those shared resources through the lifespan context, so setup and teardown live in one clear place instead of scattered callbacks. When a client first connects, the server and client exchange capability lists. The server declares which primitives it supports, tools, resources, or prompts. The client inspects the list and decides which ones it will use. It won't appear in the capability list, and the client won't be able to call it.

**[05:48]** This handshake is also where the server announces its name and version, which appears in client logs and debugging tools. Three initialization mistakes come up repeatedly. The first is registering tools after run is called. The capability handshake happens at connection time, so any tool you add afterward is invisible to the client. The second is blocking the event loop inside a tool handler with synchronous I-O, like a file read or a database query, using a sync library.

**[06:29]** One blocking call stalls every other request the server is processing. Use async libraries or wrap sync calls with run in executor to avoid this. The third is leaving tool handlers without explicit error handling. The MCP server class does catch unhandled exceptions and surface them as error results, so the server keeps running, but you should still handle errors yourself, raising tool error or masking details to return clean, actionable messages and avoid leaking internals to the client. Standing up a server and writing a tool are different jobs, and the skeleton is the one that people rush. **[00:00]** MCP servers can expose more than tools. Resources are one of the three core MCP primitives, and they give host applications a structured way to pull data from a server and inject it into model context. Coming up in this video, we'll cover how resources are defined, what URI schemes and MIME types do, and the difference between static and dynamic content. A tool is something the model reaches for. A resource is something the application hands over, and that difference drives everything else about how resources behave. An MCP resource is a URI addressable data object that a server exposes so the host application can inject it into context.

**[00:45]** It's application controlled, which means the host decides what gets pulled in, not the model. Each resource is reached through a URI scheme, the protocol prefix-like file, DB or config, that tells a client how to interpret the address. And each one carries a MIME type, a standard label like text slash plain, or application slash JSON that declares the format of the content coming back. Together, they form the contract between the server that owns the data and the host that decides when to use it. A resource definition has only two required fields. The URI is the stable address a client uses to request that resource, and the name is a human readable label that identifies it.

**[01:30]** Those two are all the spec demands. The MIME type is optional. When you include it, it helps the host interpret the content it gets back, telling it whether to treat the payload as plain text, JSON, or something binary. But the resource is still perfectly retrievable without one. Behind the scenes, a content handler on the server produces or fetches the data when a client calls resources slash read. So think of URI and name as the contract and MIME type as helpful metadata that makes the returned content easier for the host to handle correctly.

**[02:04]** The most important design decision for any resource is whether it's static or dynamic. Static resources hold content that doesn't change between requests. Configuration files, fixed reference tables, and policy documents are typical examples. Because they're stable, they can be cached safely and don't require a live handler to run on every call. Dynamic resources are the opposite. They're generated or fetched at request time, so the content can differ from one call to the next.

**[02:36]** Database query results, live API responses, and user-specific data all fall into this category. Caching a dynamic resource without an expiry policy is a common mistake that causes models to work with stale context. URI scheme design matters more than it might seem. A well-designed scheme is self-describing and domain consistent. Using db colon slash slash for database records, file colon slash slash for file system content, and config colon slash slash for configuration snapshots makes the source of a resource obvious from the address alone. Stability is equally important.

**[03:17]** If a URI changes between server versions, any client logic that cached the old address breaks silently. You should also avoid embedding volatile state, like session tokens or timestamps, directly into the URI path. Stable URIs let host applications build resource injection rules once and rely on them across deployments without ongoing maintenance overhead. A consistent scheme also makes it easier to write access control rules that apply across all resources of the same type. Here's a practical problem. A single resource entry points at one fixed URI, but a server often holds thousands of files or records.

**[03:56]** You can't list them all in advance. That's what resource templates solve. A template exposes a parameterized URI with a named placeholder written in the standard URI template syntax, so file colon slash slash slash open brace path, close brace stands in for any path. The client discovers these templates through a distinct call, resources slash templates slash list, which is separate from the plain resources slash list. Once the host knows the template, it fills in the parameter, say the actual file path, and then calls resources slash read on that concrete URI. So templates give you a compact way to advertise a whole family of addressable resources without enumerating everyone up front.

**[04:47]** There are three resource types you'll encounter most often in MCP server designs. File resources use the file colon slash slash scheme and return plain text or binary content with a content type of text slash plain or application slash octet stream. Database records use a db colon slash slash scheme and return query results as JSON with a content type of application slash JSON. Config snapshots use config colon slash slash and return structured key value content from a configuration store. Each type pairs a scheme with a predictable MIME type, which makes it straightforward for host applications to route the content to the right part of the model's context without inspecting the payload on every call. MCP supports resource subscriptions, which solve a real problem with dynamic content.

**[05:42]** Without subscriptions, the only way to keep a resource current is to pull, fetch it on every request, and hope the version in context is fresh. With subscriptions, a client registers interest in a specific URI after the first retrieval. When the server detects that resource's content has changed, it sends a notification to the subscribed client. The client then refetches the updated content using the same URI. This pattern keeps dynamic resources fresh without unnecessary polling and without flooding the server with repeat read calls when nothing has changed. Exposing a resource from a server involves three implementation steps.

**[06:26]** First, you declare the resource in the server's resource list at startup so clients can discover it when they call resources slash list. Second, you implement a read handler that accepts a URI and returns the resource content, along with the appropriate MIME type. Third, if the resource is dynamic and change notifications matter for your use case, you implement a subscribe handler that manages client registrations. The host application orchestrates all of this by calling resources slash list to see what's available and resources slash read to retrieve specific content when it decides to inject it. The application controlled nature of resources is the distinction people most often get backwards. The host application decides which resources to retrieve and when to inject them into context.

**[07:18]** The model doesn't invoke resources the way it invokes tools. Once the host has injected resource content into the conversation, the model reads it as it would any other context, but it didn't select it. This is the key distinction between resources and tools. Tools are model controlled. Resources are application controlled. The host selects.

**[07:36]** The model reads. Confusing these two control models is the mistake that comes up most often when people first work with resources. Keep the control points sharp. The application controls resources and the model controls tool invocations. Resources give a host application an addressable way to pull server data into model context. That matters because the control points sit with the application, not the model.

**[08:08]** The model reads what it's handed and it never goes shopping for a resource on its own. One thing to watch is that mixing up that control point is the most common misread of the primitive. That's a wrap on this lesson. I'll see you in the next one.

**[00:00]** MCP prompt templates are the third of the three MCP primitives, alongside tools and resources. They're reusable, parameterized prompt instructions stored on a server that users can select to pre-populate an interaction. In this lesson, we'll cover how templates are defined, how arguments work, and the scenarios where server-side prompts add real value. The word prompt does a lot of work in this space, so it helps to pin down what it means inside MCP. An MCP prompt is one of the three MCP primitives, a reusable, parameterized template stored on a server that users select to pre-populate an interaction. The critical word is user-controlled because a human explicitly chooses to apply it.

**[00:48]** That is what separates it from resources, which the host injects, and tools, which the model invokes on its own. Prompt arguments are the named, typed parameters the client fills in before the template is rendered. And prompt rendering is the server-side step of substituting those argument values into the template body and returning the completed prompt to the client. Every MCP prompt template definition has three components. The name is the stable identifier that clients use to request the template when they call prompts slash get. The arguments list declares the named parameters the template expects, along with their types and any default values.

**[01:30]** And the template body is the actual prompt text, with placeholders for each argument that gets substituted at render time. When a client calls prompts slash get with the template name and a set of filled argument values, the server substitutes those values into the body and returns the fully rendered prompt. The client then injects that rendered prompt into the conversation as the opening instruction context. Understanding how prompts differ from the other two MCP primitives matters for the exam. Prompts are user-controlled. The human explicitly selects a template from a list surfaced in the host UI, and the system pre-populates the interaction with it.

**[02:11]** Resources are application-controlled. The host decides which data objects to retrieve and inject. The user doesn't necessarily know it's happening. Tools are model-controlled. The model decides when to invoke a tool based on what it needs to accomplish. Three primitives, three control points, user, application, and model.

**[02:33]** Keeping these distinctions clear is exactly what the Architect Foundation's exam tests in this area. Server-side prompt templates are most valuable when task instructions are complex, long, or need to be consistent across many users. Multi-step analysis workflows benefit enormously from a structured template that enforces a repeatable methodology instead of relying on each user to retype a long instruction set.

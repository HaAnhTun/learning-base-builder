## 114. When to Escalate — Trigger Design

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 114/136 · en_US · auto caption

**[00:00]** In this lesson we're looking at escalation trigger design. Agents that try to handle everything on their own eventually produce bad output silently or get stuck in retry loops. We'll cover the trigger categories that hold up in production, the difference between hard and soft triggers, and how to give an agent a clean way to escalate deliberately. An instruction like escalate when you're unsure sounds reasonable and is close to useless because a model can't act on it consistently. What works instead is an escalation trigger, an explicit condition that causes the agent to hand off control rather than keep executing. The key word there is explicit.

**[00:36]** A confidence gate is one such condition. Firing when the agent's own confidence score falls below a threshold you define in the system prompt. Out-of-policy detection is another. Firing when the requested action hits a deny list or falls outside an allow list. Together they cover most of what you need to build a trigger set that actually holds up in production because each one names a condition the model can check rather than a feeling it has to interpret. Every escalation system fails in one of two directions.

**[01:12]** The first failure mode is never escalating. The agent keeps going, produces output, and the output reaches users even when it's wrong. This is the silent failure. It's the harder one to catch because there's no alert, no flag, just a bad result that a user may or may not notice. The second failure mode is escalating too often. When every ambiguous step triggers a handoff, reviewers get overwhelmed and start ignoring alerts.

**[01:38]** The alert channel loses value. Good trigger design sits between these two extremes. You want the agent to escalate exactly when it genuinely can't proceed safely and not before. Hard triggers and soft triggers work differently and the difference shapes how you write your system prompt. A hard trigger is a policy condition with no model judgment involved. If the requested action hits a deny list, the agent escalates.

**[02:07]** Full stop. An allow list is the same idea in reverse, permitting only the actions on the list, so anything else escalates. Both lists live in the system prompt, so the agent looks them up rather than reasoning about them. That predictability is the whole point. A soft trigger is different. It invites model judgment.

**[02:27]** If the agent's confidence is below a threshold or if the user's intent is ambiguous, the agent decides whether to escalate based on its read of the situation. You can tune that threshold over time as you observe how the model handles edge cases in your workflow. Confidence gates are one of the most useful trigger patterns. The idea is straightforward. The agent attaches a confidence estimate to each step and if that estimate drops below a threshold you've set in the system prompt, it escalates instead of proceeding. The threshold is something like escalate if confidence is below 0.7.

**[03:05]** That number lives in the policy, not in the model's judgment. The tricky part is calibration. A confidence number is only useful if it reflects reality. An overconfident model will report high confidence even when it's guessing, so confidence gates work best when you pair them with logged reasoning. The agent explains why its confidence is low and that explanation becomes part of the escalation record. Repeated failure detection is one of the simpler trigger patterns to implement and it catches a failure mode that's easy to overlook.

**[03:40]** An agent stuck in a retry loop is burning context window, wasting latency, and likely heading toward a timeout. The fix is to count. Count tool errors, count validation, rejections. When that count exceeds a ceiling you've defined, the agent escalates with a record of what it tried and what failed each time. The ceiling is usually two or three attempts. The exact number depends on your use case, but the principle is consistent.

**[04:04]** A second failure is information. It tells you the problem probably isn't transient. Treating it as an escalation trigger turns a stuck loop into a clean handoff. Policy checks and retry ceilings fire on their own, without the model deciding anything. The ask for help tool is the opposite and it's worth singling out because it's the most explicit form of escalation trigger available. Instead of hoping the model will recognize an edge case and handle it gracefully, you define a tool in the system prompt called something like escalate or request review.

**[04:40]** The model can call it just like any other tool it has access to. When it does, it logs the decision, the context, and the reason all in one step. That's the advantage over softer signals. A called function produces a clean structured record. Compare that to an agent that writes a free text message explaining why it stopped, which is harder to route, harder to parse, and easier to miss. It's worth being just as precise about the triggers that should never fire because over escalation is the quieter of the two failure modes.

**[05:16]** Escalating on every uncertain step defeats the point of automating the work at all. If an action is low stakes and easily reversed, a human gate adds friction and buys you no safety in return. If a validation layer already checks something programmatically, putting a person behind it as well is redundant and it teaches reviewers that approvals are a formality. And a trigger based on gut feel rather than a defined condition fires inconsistently, which means you can't test it or reason about when it will happen. Each of these looks cautious and is actually corrosive. Here's the framing that keeps the whole thing honest.

**[05:54]** Human review is a targeted risk control placed deliberately where consequences are high and hard to reverse. It isn't a catch-all for whenever the model seems unsure. Getting the threshold right is a calibration exercise and it isn't a decision you make once. Set thresholds too tight and you get constant interruption, reviewers stop reading and the automation stops earning its keep. Set them too loose and real risk walks straight through the gate unchecked. So watch your escalation rates and production and tune them against what reviewers actually report.

**[06:32]** The threshold that is right today can be wrong once the workflow around it changes. A trigger is the moment an agent admits it shouldn't be the one deciding. Getting that moment right is the whole game because you can miss it in both directions. Silence ships bad output nobody reviewed and noise trains your reviewers to approve on reflex. Just remember a trigger that fires on something reversible costs attention and buys you nothing. That wraps up this one.

## 115. The Handoff Payload — What the Next Actor Needs

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 115/136 · en_US · auto caption

**[00:00]** We'll spend the next few minutes going over what happens after an escalation fires. The handoff payload is what determines whether the next actor can actually resolve the situation or has to reconstruct the entire conversation from scratch. We'll cover the four fields a payload should have, why structure beats narrative, how routing works, and how to close the loop when a resolution comes back. An escalation is only as good as the bundle it hands forward. That bundle is the handoff payload, the structured package of context, history, and suggested next step that an agent passes on when it escalates. The word structured is doing real work there.

**[00:43]** A free text block and a schema with defined fields are very different things, and they produce very different outcomes for whoever receives them. Escalation routing is how that payload gets directed to the right next actor based on what it contains. And closing the loop is the return trip, re-injecting the reviewer's or supervisor's response back into the original agent's context once the escalation resolves. Without that last step, an escalation is a one-way street and the agent never learns what was decided. A handoff payload needs four things. First, a conversation summary, a compressed account of what happened before the escalation fired.

**[01:27]** Second, the triggering question. Preserve it verbatim. Don't summarize it and don't paraphrase it because the reviewer needs to see exactly what the agent saw at the moment the trigger fired. Third, what the agent tried, and that's a log rather than a summary. Each tool call made, each validation run, each retry attempted, along with what it returned because that log is how the reviewer knows what not to bother trying again. And fourth, a suggested next step.

**[01:57]** Agents often skip this one since they escalated precisely because they didn't know what to do, but even an uncertain hypothesis gives the reviewer somewhere to start. Structured handoffs and narrative dumps aren't equally useful, and the difference shows up immediately when you try to route or aggregate them. A structured handoff has defined fields. The receiver can parse it, route it to the right queue, and extract the fields they need without reading everything. An automated system can do that routing too. A narrative dump is a free text block.

**[02:31]** It might contain everything, or it might omit the one detail the reviewer needed most. It can't be parsed reliably, can't be routed automatically, and can't be aggregated into metrics. When you're looking at the data across 100 escalations, free text is nearly useless. Structure wins because it's designed for the receiver, not for the agent that produced it. Once a payload is structured, routing becomes straightforward. The orchestrator inspects the payload and directs it to one of three destinations.

**[03:02]** Human reviewer is the right destination when the escalation requires judgment or authority that a model shouldn't exercise. A specialist agent is the right destination when the issue falls within another agent's defined domain. A supervisor model is the right destination when the escalating agent hit its capability limit, but a more capable model might be able to proceed. The routing logic lives in the orchestrator, not in the escalating agent. The agent's job is to produce a clean payload. The orchestrator's job is to send it somewhere.

**[03:36]** Keeping those responsibilities separate makes both components easier to test and easier to change. Three failure patterns show up repeatedly in handoff designs. Missing context is the most common. The payload describes what failed, but omits enough of the conversation history that the reviewer has to go back and read the whole thing anyway. That defeats the purpose of a structured handoff. The second failure is no suggested step.

**[04:04]** The agent describes the problem, but offers nothing on what to do next. The reviewer is left to figure that out alone. The third failure is an unroutable format. A free text payload can't be parsed by the routing layer, so it lands in a generic queue instead of the right inbox. All three failures come from designing the payload for the agent's convenience, rather than the receiver's needs. Every escalation is a data point.

**[04:30]** An agent that escalates repeatedly on the same trigger category is telling you something about your prompt, your policy, or your threshold settings. The only way to see that pattern is to log each handoff and aggregate over time. Log the trigger type, the payload fields, the routing destination, and the resolution. Aggregate that data across sessions, and you'll find patterns quickly. Maybe one trigger category is responsible for 60% of your escalations. That probably means the threshold is set too low, or there's an allow list gap.

**[05:05]** Maybe escalations to the supervisor model almost always resolve successfully, which suggests the issue is capability, not policy. Routing turns individual escalations into systemic improvements to your agent design. Closing the loop is the step that most agent designs omit. After a human reviewer or supervisor model resolves the escalation, that resolution needs to come back to the original agent. The injection point is the same context window the agent escalated from. The reviewer's answer gets appended, and the agent resumes with that new information.

**[05:42]** When we talk about loop closure, the agent restarts from its pre-escalation state. It doesn't know what the reviewer decided. It might escalate again on the same trigger, or it might proceed incorrectly because it never received the resolution. With loop closure, escalation becomes a recovery mechanism. The agent hits a limit, gets help, and continues. That's the design goal for any agent that needs to handle complex multi-step tasks reliably.

**[06:10]** A well-structured handoff payload gives the next actor everything they need to act without starting over. A defined set of fields instead of a narrative dump, clear routing to the destination that can actually resolve the issue, and loop closure at the end are what turn an escalation into a recovery mechanism, rather than a dead end. Build the payload for the receiver, not for the agent that produced it. That wraps up this lesson. I'll see you in the next one.

## 116. Where to Catch the Error — Local or Up the Stack

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 116/136 · en_US · auto caption

**[00:00]** In this lesson, we're looking at one of the most consequential design decisions in the multi-agent system. When a sub-agent hits an error, does it handle that error itself, or does it surface the failure to a coordinator? The answer isn't obvious, and getting it wrong in either direction can cause real problems. Let's map out the decision space. Every sub-agent failure ends up in one of two places, and the architect decides which. Local recovery means the sub-agent catches the failure, handles it internally, and returns to the coordinator as if nothing happened.

**[00:35]** Coordinator propagation means the sub-agent surfaces the failure, passes structured information upward, and lets the higher-level plan adapt. In between those two sites, the propagation boundary, the interface where the architect decides, deliberately, which failures cross up and which stay contained. That boundary isn't a runtime behavior, it's a design choice, and it should be documented, tested, and enforced. Most production failures in multi-agent systems trace back to a propagation boundary that was never consciously set and defaulted to one extreme or the other. Teams that skip a deliberate policy land on one of two extremes, and both have a name, Silent corruption happens when a sub-agent catches every exception and returns a vague success. The coordinator proceeds on the assumption that the task completed correctly, but the data it's planning on may be malformed, incomplete, or simply wrong, and the defect hides until it causes downstream failures that are far harder to diagnose.

**[01:41]** Coordinator thrash is the opposite. Every internal hiccup propagates. A rate limit pause, a minor validation issue, a transient timeout, all flow up as error events. The coordinator retries and escalates constantly, which masks the signal from the failures it should be acting on. Neither extreme is a strategy. What you want is a deliberate boundary between them.

**[02:04]** So what belongs at the local recovery level? Retryable transients are the clearest case. A retryable error is one where repeating the same call without changing anything might succeed. If the sub-agent hits a rate limit and waits 200 milliseconds before going through, the coordinator doesn't need to know. That blip resolved itself. Recoverable validation failures are similar.

**[02:28]** If the agent receives malformed input, it can sanitize and reprocess. That's an internal correction, not a system-level failure. Idempotent refetches fall in the same category. The key test is whether the coordinator's plan depends on knowing this happened. If handling it locally leaves the coordinator with accurate information and a valid path forward, local recovery is the right design choice. On the other side of the boundary, some failures carry information the coordinator's plan genuinely depends on.

**[03:01]** Scope violations are the clearest example. If a sub-agent is asked to perform an action outside its authorization, that's not a transient blip, and the coordinator's task decomposition may need to change entirely. Policy denials fall in the same category because a guardrail blocked the action permanently, and no retry will change that outcome. Those are non-retryable errors. Repeating the same call produces the same failure, so every sub-agent needs a retry budget. A maximum number of local attempts before it stops and hands the failure upward.

**[03:36]** Once that budget is spent with no progress, the coordinator needs to know so it can reroute, substitute a different agent, or escalate. Here's a practical test you can apply to any failure mode in your system. Ask, would the coordinator's higher-level plan change if it knew this happened? If yes, propagate. The failure affects scope, sequencing, or resource allocation, and surfacing it lets the coordinator adapt correctly. If no, recover locally.

**[04:07]** The failure is fully resolved inside the sub-agent's own retry or sanitization loop, and the coordinator receives accurate results regardless. If you're genuinely unsure, default to propagating with a low severity signal. Visibility is almost always safer than silence. An operator can dismiss a low-priority warning. No one can act on a failure that was never reported. When in doubt, let it surface with a clear label attached.

**[04:34]** One principle often gets skipped. Even when a sub-agent recovers locally, that recovery should leave a structured trace. Logging at the boundary isn't optional. The sub-agent should record the failure type, the timestamp, and how many retries it took before returning success. Why? Because patterns in local recoveries are diagnostic signals.

**[04:58]** If a particular sub-agent is retrying three times on nearly every call, something upstream is degraded, and no one can see it without logs. A silent local recovery with no trace is the first step toward the silent corruption we talked about earlier. The coordinator may not need to act on every recovery event, but the operator always needs visibility into how the system is actually behaving in production. The propagation boundary is a design decision, not a default. A deliberate policy prevents both silent corruption and coordinator thrash. Ask whether the coordinator's plan would actually change.

**[05:39]** Log transient recoveries local, propagate scope violations, policy denials, and exhausted retry budgets, and log every local recovery so operators can see the pattern before it becomes an incident. That wraps up this lesson. I'll see you in the next one.

## 117. Designing the Propagation Contract

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 117/136 · en_US · auto caption

**[00:00]** An error that propagates is only useful if the coordinator can act on it. The propagation contract defines the error envelope structure, how severity levels map to coordinator policies, how partial success state prevents duplicate work, and why item potency is non-negotiable when retries are part of your recovery design. Let's build this out. When a failure crosses the boundary, it should arrive as a package the coordinator can act on. That package is the error envelope, a structured object that carries failure information from a sub-agent to its coordinator. Think of it as a formal handoff, with typed fields rather than a free text string.

**[00:43]** Severity level is the classification embedded in that envelope. It can be warning, recoverable, or fatal, and each level maps to a specific coordinator action. Map mapping is the policy, and it has to be designed ahead of time, not improvised at runtime. Item potency is the third piece, the guarantee that retrying an operation produces the same outcome as running it once. It's what keeps a coordinator retry from causing double writes, duplicate charges, or conflicting state. Let's look at what a well-designed error envelope contains.

**[01:20]** The most important field is error type, a machine-readable category that the coordinator can branch on programmatically. This is what allows automated recovery without parsing free text messages. The second field is severity, which drives the coordinator's response policy. The third field is context, the sub-agent identifier, the task reference, and enough of the relevant input state that the coordinator can reconstruct what was happening when the failure occurred. Some envelopes also include a recovery hint field, a structured suggestion from the sub-agent about what the coordinator might try. The coordinator isn't obligated to follow the hint, but having it available speeds up automated recovery decisions considerably.

**[02:07]** Here's why the envelope structure matters so much. When a coordinator receives a structured error object, it can branch deterministically. It reads the severity field, looks up the matching policy, and executes the appropriate response, retry, fallback, or escalate. That logic is testable, auditable, and fast. When the coordinator receives an unstructured string, something like operation failed in step 3, it can't route reliably. A human has to read it and decide what to do next.

**[02:41]** Automated recovery becomes impossible without brittle string matching that breaks the moment someone changes a log message. The difference between structured and unstructured error propagation is the difference between a system that recovers automatically and one that requires human intervention every single time. The severity levels in the error envelope each map to a specific coordinator behavior, and that mapping has to be defined in the system design, not discovered at runtime. A warning level means the coordinator logs the event and continues executing. Something stops. A recoverable severity means the coordinator should attempt recovery, typically by retrying with exponential backoff or routing to a fallback agent.

**[03:27]** The task may still complete, just via a different path. A fatal severity means the coordinator halts the dependent task chain. It can't proceed safely, and it escalates to a human operator who can make a judgment call. The insight here is that severity without a corresponding policy is meaningless. Labels only matter when they trigger defined behavior. When the coordinator decides to attempt recovery on a propagated failure, it has four main options.

**[03:57]** Exponential backoff means retrying the same sub-agent with increasing wait intervals between attempts. This works well for transient resource constraints like rate limits or temporary unavailability. A fallback agent routes the task to an alternate implementation, perhaps a different model or a rule-based system, when the primary agent is consistently failing. Partial completion acceptance means the coordinator takes whatever work the sub-agent completed and adjusts the remaining plan to skip the failed step. And human escalation pauses the task chain entirely and surfaces the failure for a judgment call that automated policy can't make. A well-designed coordinator has all four available and selects based on severity and error type.

**[04:43]** Multi-step sub-agent tasks introduce a specific complication. What happens when the failure occurs partway through? A sub-agent might complete steps 1 through 3 successfully before failing on step 4. If the coordinator retries the entire task, steps 1 through 3 execute again, and whatever side effects they produced are now doubled. The solution is to include a completed steps field in the error envelope. This tells the coordinator exactly how far the sub-agent got before failing.

**[05:14]** The coordinator can then retry starting from step 4, or route a different agent to pick up from that point. Without this field, the coordinator has no way to distinguish failed at the start from failed after most of the work was already done. And safe resumption isn't possible. One more safeguard deserves its own treatment because it's what makes coordinator retries safe when sub-agents interact with external systems. Consider a sub-agent that writes a record to a database, sends an API request, or places a message on a queue. If the coordinator retries that sub-agent after a propagated failure, without idempotency, the external write executes a second time.

**[05:55]** The record is duplicated. The charge is doubled. The message is sent twice. IPC keys solve this by giving each operation a unique token. The sub-agent checks whether it has already completed an operation with that token before executing. If yes, it returns the previous result without re-executing.

**[06:16]** The coordinator passes the same token on retry, and the sub-agent handles the rest. This has to be designed in from the start. The final piece of the propagation contract is observability. The ability to trace an error from a leaf agent all the way through the coordinator to the user-visible result. In a multi-agent system with several layers of nesting, a failure at a leaf can travel through multiple coordinators before it surfaces. Without deliberate instrumentation, debugging that path is nearly impossible.

**[06:47]** The solution is span-based tracing. Each agent adds its own span identifier to the error envelope before propagating. The coordinator links these spans into a distributed trace that covers the full call chain. When an operator investigates a failure, they can follow a single request through every agent hop and see exactly where it broke and why. Without this, debugging a propagated error means guessing at the source. A propagation contract turns the boundary into an interface instead of an accident.

**[07:20]** The point is that the answers get decided while the system is calm. Who owns the recovery? What a retry is safe to repeat. Settle that in advance and you're not writing policy while an outage is running. That does it for this one. I'll see you in the next lesson.

## 118. The Silent Bug — When 'Nothing' Is Ambiguous

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 118/136 · en_US · auto caption

**[00:00]** A tool returns nothing. That single result can mean two completely different things and an agent has no way to tell the difference. This is a silent bug and it's one of the hardest failures to catch in production. For the next few minutes we'll look at how it happens and what it can cost you. Let's get into it. Picture a search that comes back with nothing.

**[00:16]** The agent can't see whether the data source was checked and came up empty or whether the tool never reached it at all. An access failure is when a tool call doesn't successfully reach the underlying data source. Connection refused. Credentials rejected. Request timed out. The tool never got to search.

**[00:32]** An empty result is the opposite. The tool reached the data source just fine and confirmed there is nothing matching your query. That is a legitimate answer. The silent false negative is what happens when an agent reports nothing exists because a tool failed silently rather than because the data is genuinely absent. Keep those distinct in your mental model and the rest of this lesson follows naturally. Let me give you a concrete picture of how this bug happens.

**[01:01]** Imagine a search tool that queries a vector index for relevant documents. At some point during an agent session the index service goes offline. The tool still runs. It sends a query but instead of getting search results it gets a connection error internally and it returns an empty list to the agent with no error flag attached. The agent reads that empty list. It has been instructed to trust tool results so it concludes that no documents exist and moves forward confidently with that conclusion.

**[01:37]** The silent bug is now alive in the session. The failure and a successful empty search look identical from the agent's perspective. That is the core problem we're solving in this lesson. The distinction between these two outcomes is the most important idea in this lesson. An access failure means the tool couldn't reach the data source. The empty response reflects a connection problem not a content gap.

**[02:02]** Retrying the call is appropriate and the agent shouldn't draw any conclusions about what exists or doesn't exist in the data store. An empty result means the tool successfully reached the data source and confirmed there is nothing matching the query. That is a valid answer. Retrying is wasteful. The absence is meaningful information. The problem is that without explicit signaling both outcomes look like an empty list to the agent.

**[02:27]** It can't tell them apart on its own. You have to build that distinction into the tool response. Why do agents default to treating an empty result as nothing exists? Because that is what the prompt and the model's pattern matching push them toward. An empty list is a data signal. The model is trained to treat data signals as ground truth.

**[02:52]** When a tool returns an empty list the implicit message is I searched and found nothing. There is no error flag, no exception, no branch pointing to a failure path. So the agent proceeds confidently. It has no mechanism to ask wait did this tool actually connect? Without explicit support for that question built into the tool response the model can't distinguish ambiguous nothing from confirmed nothing unless the tool response is designed to make that distinction visible. That design choice is the entire fix.

**[03:22]** Access failures come in four main categories and each one produces an empty or incomplete response that looks like a successful query from the outside. Connection errors happen when the network or service endpoint is completely unreachable. The tool never connects and returns nothing. Auth failures happen when credentials are missing, expired, or revoked. The data store rejects the request before any search logic runs at all. Query timeouts happen when the data source is technically reachable but responds too slowly.

**[03:59]** The tool gives up and returns empty and partial results are the trickiest. The data source returns some records but silently truncates the rest due to an internal limit or error. All four of these categories need to be caught at the wrapper layer and labeled explicitly before the agent sees the response. Let's talk about the phrase the agent says when this goes wrong. I couldn't find anything. That sentence implies a successful search with no matches.

**[04:24]** The user hears that and concludes the information doesn't exist. They make decisions based on that conclusion. If the real cause was an access failure, those decisions are built on a false premise. The correct response to an access failure is something like I was unable to check or the search tool didn't complete successfully. Those phrases are truthful and they put the user on notice that the absence of information isn't a confirmed fact. The distinction isn't pedantic.

**[04:55]** It is the difference between a trustworthy agent and one that silently misleads users at exactly the moments they're relying on it most. The production cost of getting this wrong is high and it is delayed. When an agent returns a confident false negative, no exception is raised. The logs look clean. The tool ran. The agent responded.

**[05:20]** Everything appears to have worked correctly, but the user walked away with incorrect information and whatever decision they made based on that information is now in the world. When you try to trace back a bad decision days or weeks later, you're looking for a silent failure in an agent session that left no error trace. That is extremely hard to debug and the compounding effect is worse. Users stop trusting the system after a few experiences like this, even when they can't name exactly what went wrong. Silent false negatives erode trust faster than any visible error message. An empty tool result is an unanswered question, not an answer.

**[05:56]** The tool either confirmed nothing's there or never reached the source and those two carry opposite meanings. That matters because your user hears I found nothing either way and acts on it. Just remember no exception fires here, so the bad decision is already in the world before anyone notices it. That's it for this lesson. I'll see you in the next one.

## 119. Disambiguation Patterns and Tool-Wrapper Discipline

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 119/136 · en_US · auto caption

**[00:00]** This lesson walks through building the fix into the tool layer, where an ambiguous empty result can be caught before it ever reaches the agent. We are going to walk through the wrapper patterns, the status schema, the retry rules, and the logging practices that together make ambiguous nothing impossible to return. Let's get into it. The fix for this bug is structural, and it lives in the plumbing between the tool and the agent. A tool wrapper is a thin layer sitting there. It does one job.

**[00:26]** It normalizes the response, attaches a status field, and enforces disambiguation before the agent sees anything. A status enum is the structured field the wrapper attaches. It labels the outcome class explicitly, so the agent branches on that label rather than inferring meaning from an empty data payload. And retry discipline is the rule that governs what happens next. Empty results don't trigger retries. Access failures do, up to a configured limit.

**[00:57]** That rule has to live in the wrapper, not the agent prompt, or it will be applied inconsistently across sessions and tool calls. The first wrapper rule is distinguishing HTTP success with an empty body from HTTP failure. These are fundamentally different outcomes, and they need to be treated differently at the wrapper layer. A 200 response with an empty list is a valid empty result. The server processed your query, checked the index, and came back with nothing. That is meaningful information.

**[01:29]** A 4x or 5x response is an access failure, regardless of what the body says. The data source rejected or couldn't process the request, and a timeout is an access failure, even when no HTTP status code is returned at all. The wrapper catches all three of these cases and maps each one to the correct status field before the agent ever sees the response. That mapping is the core of the wrapper contract. The status enum has four outcome classes, and each one has to be named explicitly in the agent prompt. Success means the tool reached the data source and returned matching results, so the agent proceeds normally.

**[02:13]** Empty result means the tool reached the source and confirmed no matching content exists, so the absence is a real answer. Partial result means the response was truncated, so the agent flags that the answer may be incomplete. Access failure means the tool never reached the source, so the agent draws no conclusions, applies the retry policy, and tells the user it couldn't check. Implicit defaults are where the bug re-enters. Leave any one of those branches unnamed, and the model fills the gap with its own assumption. Retry policy is one of the clearest expressions of the disambiguation principle in practice.

**[02:51]** Empty results don't retry. If the data source confirmed there is no matching content, running the same query again against the same index produces the same empty result. Retrying wastes latency and burns through quota with zero benefit to the user. Access failures are different. The data source was unreachable, and that condition may be transient. A network blip, a brief service restart, or a temporary credential expiration can all resolve on their own.

**[03:20]** Retrying with exponential backoff is appropriate, up to a configured limit. Once that limit is hit, the wrapper should escalate, return an access failure status, log the exhausted retries, and surface the failure to the agent, rather than silently returning empty to the caller. Every access failure needs a structured log entry at the moment it occurs, not reconstructed later from the agent's output. The log entry should capture four things. The timestamp of the failed call, the tool name and target endpoint, the error class, timeout, auth, connection, or partial, and the retry strategy that was applied along with its outcome. Without this log, post-incident diagnosis becomes guesswork.

**[04:01]** From the outside, the agent session looks clean. The tool ran, the agent responded. No exception was raised. The failure is invisible unless you built the trace in from the start. When you're debugging a bad decision that propagated through an agent session three days ago, a structured log is the difference between a quick investigation and a multi-day reconstruction effort. User-facing language has to track the status field exactly.

**[04:29]** Three phrases, three distinct uses. Found nothing is reserved for confirmed empty results only. When you say that, you are asserting that the search succeeded and no data exists. That phrase should never appear when an access failure occurred. Couldn't check is the correct phrase for access failures. It signals that the absence of results isn't confirmed, and the user shouldn't act on it as if it were a real answer.

**[04:59]** And partial results is what you say when the tool flagged a partial response. It tells the user that some data may be missing, and the answer they are getting isn't complete. These three phrases are the user-facing expression of the same disambiguation the wrapper enforces at the technical layer of the system. The status field in the tool response schema has to be mandatory, not optional. Optional status fields lead to exactly the failure mode you're trying to prevent. Some tool calls return a status and disambiguate correctly, and others return only data and silently revert to the ambiguous nothing problem.

**[05:37]** If the field is optional, some developer will leave it out under time pressure, and the wrapper will have no status to attach to the response. The status field should also be a typed enum, not a free text string. Strings allow access failure, access failure, failed, error, and timeout to all appear as distinct values, which breaks the agent's branching logic. A typed enum enforces exactly four valid states. The wrapper populates this field before the agent ever sees the response, and that is the contract you're enforcing. Disambiguation is an architectural commitment built into every layer.

**[06:19]** The wrapper maps outcomes to a status, the schema makes the status mandatory, the agent prompt branches on it, the retry policy respects it, and the log records it. When each of those layers enforces the same distinction between access failure and empty result, the silent false negative has nowhere left to hide. That wraps up this lesson.

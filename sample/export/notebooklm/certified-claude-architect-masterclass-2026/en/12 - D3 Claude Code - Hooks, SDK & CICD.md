## 80. Real-World Hook Applications — Logging, Linting, Safety Nets

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 80/136 · en_US · auto caption

**[00:00]** For the next few minutes, we'll dig into putting hooks to work in real engineering scenarios. We'll walk through six patterns, starting with auto-formatting on file right and blocking destructive bash commands, then logging tool calls for audit trails, notifications on task completion, automatic test runs after edits, and API cost tracking. Each pattern maps to a specific hook type. You finish a refactor and the pull request comes back covered in comments about indentation. Nobody meant to skip the formatter, they just forgot. That's exactly the gap hooks close, and a few of them do most of the work.

**[00:39]** An auto-format hook is a post-tool use hook that runs a code formatter after any file is written, so style is never a manual step. A safety net hook is a pre-tool use hook that inspects pending bash commands for dangerous patterns and stops them before they execute. An audit log hook is a post-tool use hook that records every tool call with a timestamp, leaving a traceable history of what the session actually did. Which one you reach for follows from timing. The auto-format pattern is one of the most common hook use cases. Developers forget to run formatters manually, and inconsistent style creates noise in code reviews and slows down pull request cycles.

**[01:22]** The solution is a post-tool use hook that fires after any write or edit call, then immediately runs black, prettier, or whatever formatter the project requires. Post-tool use is the write hook type here because the file already exists on disk when the hook fires. The formatter edits the saved file and the result is style compliant code on every write with zero extra effort from the developer or from Claude. It's one of the fastest wins a team can get from hooks. The safety net pattern uses pre-tool use because pre-tool use fires before the command executes. That timing is everything.

**[01:59]** The hook inspects the incoming bash command string and checks it against a list of dangerous patterns like rm-rf, drop table, format disk, and similar destructive operations. If a match is found, the hook returns exit code 2, and Claude's execution stops immediately. Exit code 2 is the one that blocks. Exit code 1 and other non-zero codes are treated as non-blocking errors, so the command still runs. A post-tool use hook can't help here because post-tool use fires after the action is already done. Prevention requires pre-tool use.

**[02:33]** Knowing which hook type to reach for based on timing is one of the most important hook concepts to internalize. Audit logging has several implementation flavors depending on what the team needs. A simple append-only log writes the tool name, arguments, and timestamp as plain text after each tool call. It's easy to implement and readable without tooling. A structured JSON log stores each entry as a JSON object, which makes it easy to filter and query programmatically. Remote logging pushes entries to an external endpoint for centralized storage across many sessions, which is useful in team environments.

**[03:15]** A stop hook adds a final summary entry when the agent finishes its run, giving the log a clean end marker. The right format depends on whether the log is consumed by humans reading a terminal or by machines running queries. It's worth being clear about when pre-tool use versus post-tool use is the right choice for logging. Pre-tool use logging records intent before execution. It captures what was attempted, including actions that were subsequently blocked. That's useful for detecting policy violations because a blocked action still leaves a record in a pre-tool use log.

**[03:51]** Post-tool use logging records results after execution. It captures what actually succeeded, including output and side effects. If you need a record of completed work, use post-tool use. If you need to catch attempted violations, pre-tool use gives you visibility into blocked actions as well as completed ones. Many teams run both hooks together to get a complete picture of agent behavior from intent all the way through execution. Notification hooks use the stop lifecycle event.

**[04:27]** Stop fires once when the agent reaches the end of its execution loop, which makes it a natural trigger for completion signals. A typical implementation calls a slack webhook, sends a system notification, or posts to a monitoring endpoint. The payload should include the task name, elapsed time, and whether the session ended cleanly or with an error. This pattern is most useful for long-running batch jobs, where the developer steps away and needs to know when results are ready without pulling the terminal. It decouples the developer's attention from Claude's execution time, which is especially valuable on tasks that take 10 or 20 minutes to complete. Test run hooks close the feedback loop between writing code and confirming it works.

**[05:13]** The hook fires post-tool use on write or edit calls, then checks the file path to decide whether to run tests. You don't want the full test suite to execute every time Claude edits a documentation file or a configuration comment. Scoping the hook to test relevant paths, like anything under SRC or lib, limits execution to meaningful changes. When the path matches, the hook runs Pytest, Jest, or whatever runner the project uses via a bash call. The developer sees test results immediately after each code edit, with no context switch required. That tight feedback loop makes it much harder for a broken test to slip through unnoticed.

**[05:52]** Cost tracking hooks monitor API usage at the session level. A post-tool use hook parses usage from the tool and transcript output where it's available, recording the model name, a timestamp, and any token counts the payload exposes. It appends that record to a session cost file or pushes it to a local database for aggregation, reviewing the data across a session, surfaces which prompts are expensive, and whether overall usage is trending toward budget limits. Teams running automated pipelines use this pattern to catch runaway sessions before they generate unexpected invoices. It's a lightweight addition that pays off quickly on high-volume workflows. Without it, cost overruns often go unnoticed until the billing cycle ends and the damage is already done.

**[06:46]** Hooks allow you to attach your own deterministic behavior to fixed points in the agent's life cycle and can be very powerful. It matters because formatting, test runs, and audit trails stop depending on someone remembering to do them. One thing to watch, the event you pick decides whether you're observing or intervening. Post-tool use can only report on what already happened. Stopping something requires pre-tool use. That does it for this lesson.

## 81. The Claude Agent SDK — Session Control

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 81/136 · en_US · auto caption

**[00:00]** This lesson walks through the Cloud Agent SDK, formerly called the Cloud Code SDK, the programmatic interface for controlling sessions from your own code. We'll look at what it can provide, how to create and manage sessions, how to stream output and tool events, and when to pick it over a direct API call. Let's get into it. What changes when the thing driving a Cloud Code session isn't a person at a keyboard? That's what the Cloud Agent SDK is for. It used to be called the Cloud Code SDK, and it's the programmatic interface that lets you integrate Cloud Code into custom applications, scripts, and pipelines.

**[00:41]** Instead of typing commands into a terminal, you call SDK methods from your code to start sessions, inject prompts, and handle output. A programmatic session is one you create and manage that way rather than through the interactive CLI. Your application decides when sessions start and stop and how their output is processed. Session streaming is the capability to receive tool call events and output incrementally as the session runs, giving you visibility into every step without waiting for a complete response. The SDK and the command line interface expose the same underlying Cloud Code capabilities. The difference is who or what is driving the session.

**[01:24]** With the CLI, a developer types commands into a terminal and reads results interactively. That works well for one-off tasks and exploratory work. With the SDK, your code calls methods, passes prompts programmatically, and processes results however your application needs. There's no terminal involved at all. Use the CLI when a human is in the loop and driving the work. Switch to the SDK when your code needs to be in the driver's seat, whether that's a script, a pipeline step, or a long-running background service.

**[01:54]** This is the decision that trips up a lot of developers. When do you use the SDK versus calling the Cloud API directly? The SDK is for agentic sessions. It manages the full agent loop, meaning multi-step tool use, file edits, shell commands, and streaming output. You give it a prompt and it handles everything in between. The direct API is for model calls.

**[02:20]** Send a prompt, get a completion. There's no session state and no built-in tool orchestration unless you build it yourself. If you need the agent loop or you need real-time visibility into what the agent is doing, use the SDK. If you need a single model call or you're building your own agent framework and want to own the orchestration, use the API. Creating a session programmatically starts with instantiating a session object in your code. You configure it with the model you want to use, the tool categories you're allowing, the working directory, and any environment variables the session needs to access.

**[02:54]** Once configured, you pass prompts as plain strings. There's no terminal, no interactive input, no manual step. The SDK handles the session loop from there. This approach makes it straightforward to embed cloud code in Python scripts, Node.js services, CI runners, or any other runtime environment that can call the SDK libraries. The session behaves the same way regardless of how it's invoked. Once a session is running, you can shape its behavior by injecting context and instructions at different points.

**[03:26]** At creation time, you pass a system prompt to establish role, tone, and behavioral constraints before any user turn begins. You can also inject file contents or directory listings, so the session starts with relevant code-based knowledge already loaded. Tool permissions are set at creation too, letting you explicitly allow or restrict read, write, and shell access to enforce safety boundaries. And you can append follow-up prompts mid-session to redirect the agent without restarting, so it keeps the context it's already accumulated. Streaming is one of the most useful SDK features for production applications. Instead of blocking until the session completes, your code receives events as they happen in real time.

**[04:14]** Tool call events fire each time the agent reads a file, writes output, or runs a shell command. That lets you log exactly what the agent is doing without waiting for the session to finish. Output chunks arrive incrementally, so you can display live progress or pipe results downstream. Error events surface failures immediately, giving your code a chance to react, retry, or alert an operator. For long-running sessions, streaming isn't a nice-to-have. It's the difference between a responsive application and one that hangs silently waiting for a final result.

**[04:49]** The SDK's primary use case is embedding clawed code capabilities into automated systems your team already owns. Code review bots can trigger SDK sessions when a pull request opens, stream the analysis, and post results directly into GitHub comments without any human intervention. Documentation generators can pass source files into a session and receive updated docs in return. CI and CD pipelines can launch clawed code sessions as explicit pipeline steps, with structured exit codes that let the rest of the pipeline react to what happened. Any workflow that benefits from agentic code understanding but needs to run inside a larger automated system is a strong candidate for SDK integration. The Clawed Agent SDK gives you full programmatic control over agentic sessions, from creation and context injection through streaming output and tool event handling.

**[05:54]** It runs the whole agent loop for you, which is the line that separates it from a direct API call. Reach for it when your code, not a human, needs to drive a multi-step workflow, and reach for the API when a single completion is all the job requires. That's it for this lesson. ## 82. Claude Code in CI/CD Pipelines

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 82/136 · en_US · auto caption

**[00:00]** This lesson covers clogged code in automated CI-CD pipelines. We'll look at why non-interactive mode is required, how the dash p flag enables it, how to structure tasks for automation, GitHub Actions integration patterns, and the security considerations that matter most in automated contexts. Let's get into it. A hung CI job doesn't fail loudly. It sits there consuming runner minutes until a global timeout kills it. Nearly every case comes down to one missing flag.

**[00:32]** The dash p flag, also called print mode, switches clogged code to non-interactive operation. Pass it and clogged code takes the prompt you give it, runs the task, prints the result to standard output, and exits cleanly. No interactive prompt, no waiting for more input. Non-interactive mode is the execution mode that dash p activates where the agent works as a one-shot tool that takes a task, completes it, and exits. A pipeline job hang is what you get when dash p is missing. Clogged code waits for interactive input the runner can never provide and the job blocks until it times out.

**[01:14]** Let's talk about why dash p is non-negotiable in automated pipelines. When a CI-CD runner launches a process, there's no human present to answer interactive prompts. Clogged code's default mode is interactive. It opens a session and waits. In a runner environment with no terminal, that wait never ends. The job hangs, consumes runner minutes, and eventually times out.

**[01:41]** The dash p flag changes this completely. It tells clogged code to run its full agentic loop non-interactively. It reads the prompt, does the work, calling tools across as many turns as the task needs, then writes output to standard output and exits with a status code the pipeline can act on. The loop still runs to completion. It just never stops to ask a human for input. That's the contract automation needs.

**[02:09]** In practice, you rarely pass dash p alone. It comes with a small set of companion flags that make a headless run predictable. Output format is the big one. Pass output format, JSON, and clogged code returns a structured result. The next pipeline step can parse instead of scraping free text. There's also a streaming variant, stream JSON, that emits events as they happen if you want live progress.

**[02:38]** Allowed tools lets you scope exactly which tools the run is permitted to invoke, which matters a lot when no human is watching. If a job should build on an earlier session, rather than start clean, resume picks up a specific past session and continue picks up the most recent one. Underneath all of them, the contract stays the same. Output goes to standard output. Exit code zero means success, and any non-zero code means something went wrong. Structuring tasks well is what makes automation reliable.

**[03:12]** Four principles matter here. First, keep each invocation atomic. One task, one outcome. Don't ask clogged code to lint a file and update documentation in the same call. Second, write prompts that are fully self-contained. The agent has no memory of previous pipeline runs unless you explicitly include that context in the prompt.

**[03:35]** Third, request structured output, usually JSON, so the next pipeline step can parse the result without brittle text matching. Fourth, design tasks to be idempotent. Pipelines retry on failure, so if the same task runs twice, the result should be the same both times. Interactive mode and non-interactive mode are worth comparing directly. Interactive mode is the default. Clogged code opens a REPL session and carries on a multi-turn conversation with you.

**[04:06]** It's designed for developer workstations, where a human is present and engaged throughout the session. You can ask follow-up questions, refine tasks, and iterate in real time. Non-interactive mode, activated by dash P, is the opposite. Clogged code accepts one prompt, does the work, and exits. There's no session, no conversation, no waiting for more input. These two modes are mutually exclusive for a given invocation.

**[04:34]** Any scenario describing automation, scheduled jobs, or CI-CD integration calls for non-interactive mode and the dash P flag. For GitHub Actions specifically, there's an official integration, and it's the path you should reach for. It's the Clogged Code Action workflow, and you set it up by running the install GitHub app command, which wires up the action and the GitHub app for you. Once it's in place, you trigger Clogged Code by mentioning at Clogged in an issue or pull request, or by passing a prompt directly to the action. You still store your Anthropic API key as a GitHub Actions secret, so it never lands in your workflow file. Now, you can run a raw Clogged dash P command inside an action step, but that's really just general agent SDK automation running in CI, not the documented GitHub Actions integration.

**[05:31]** When a scenario points specifically at GitHub Actions, reach for the official action. In automated contexts, permission scoping is a security requirement, not just a best practice. The principle is minimum necessary permissions. If your task only needs to read files, don't grant write access. If the task is purely file-based, restrict or disable network tools. If Clogged Code only needs to touch one directory, scope it to that directory.

**[06:02]** Why does this matter in automation? Because pipelines run unattended. If a task behaves unexpectedly due to a bad prompt or unexpected input, narrow permissions limit how much damage can happen. Broad permissions in an automated context are a risk you don't need to take. Let's talk about output parsing and error handling, because these are where automation breaks down in practice. Capture Clogged Code's standard output into a shell variable or a file immediately.

**[06:32]** Don't assume it will always return structured data. If something goes wrong, the agent may return a plain error message. Check the exit code after every invocation. A non-zero exit should fail the pipeline step. If you requested JSON, validate its shape before using it downstream, and always set a timeout on Clogged Code pipeline steps. A task that stalls for any reason will hold up your entire pipeline until the runner's global timeout fires, which is usually much longer than you want.

**[07:03]** Automation asks you to think about Clogged Code differently. It isn't something you talk to. It's a step in a pipeline that either finishes or fails. That one shift is what makes headless runs work, because a step that can pause to ask a question is a step that'll sit there burning runner minutes until a timeout kills it. Scoping, parsing, and timeouts all follow from taking that seriously. That closes out this lesson.

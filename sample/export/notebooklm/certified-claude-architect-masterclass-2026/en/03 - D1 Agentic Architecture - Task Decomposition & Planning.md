**[03:07]** You need to define subtasks, their inputs, their outputs, and the handoff schemas between them. That's real investment, but each piece is independently retryable. The overhead is real, but so is the resilience you get in return. Before you decompose anything, you need to analyze the goal's structure. There are three questions worth asking.

**[03:39]** First, can any part of this goal run independently, without needing output from another part? If yes, you have a candidate for parallel decomposition. **[04:12]** These three questions give you a structural map of the goal before you write a single line of orchestration code. Decomposition is really a question about where work should split.

## 11. Decomposition Patterns — Hierarchical, Sequential, and Parallel

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 11/136 · en_US · auto caption

**[00:00]** In this lesson we walk through the three decomposition patterns you'll see in almost every agentic system. Hierarchical, sequential, and parallel. We'll look at how each one works, when to apply it, how real systems combine all three, and which anti-patterns to watch out for. Let's get into it. Almost every decomposition you'll ever design is one of three shapes, or a mix of them. Hierarchical decomposition recursively splits goals into sub-goals across multiple levels, creating a tree where each level handles only its own tier of complexity.

**[00:36]** Sequential execution runs tasks in a defined order, each one potentially depending on the output of the step before it, and that dependency is exactly what forces the sequence. Parallel execution runs independent tasks at the same time, cutting total wall clock time, but introducing the need for synchronization when the branches converge back into the main workflow. Keep those shapes distinct in your head because real systems mix all of them, and you need to see which one applies where. Hierarchical decomposition builds a goal tree. At the top you have the high level goal. Below it, sub-goals.

**[01:12]** Below those, tasks. Below those, individual steps. The orchestrator at each level holds only its tier of complexity, and doesn't need to know the details of how lower levels execute. It delegates down and waits for results to flow back up. This mirrors how real organizations delegate work. An executive sets a strategic goal, a manager breaks it into projects, a team breaks those projects into tasks, and individuals handle specific steps.

**[01:43]** The advantage of this structure is specialization at each level. The risk is that coordination overhead grows with every layer you add, and errors at the bottom have to travel all the way back up before they're handled. One of the most important design decisions with hierarchical decomposition is how deep to go. Going deeper adds specialization. You can route sub-goals to agents that are purpose-built for that specific tier of complexity, and they don't have to deal with the broader context above them. But each added level increases what's called the error propagation surface.

**[02:20]** An error at the bottom of a five-level hierarchy has to travel back up through four orchestration layers before it's caught. Each of those layers is a chance for the error to be misinterpreted or swallowed. Flatten wherever you can. If two adjacent levels would run the same type of agent with nearly the same prompt, there's no reason for the separation. Depth should earn its cost through genuine specialization gains, not just because it looks clean on a diagram. Sequential decomposition is the straightforward pattern.

**[02:50]** Step 1 runs, produces output. Step 2 takes that output as input, produces its own output, and so on down the chain. The key characteristic is that step order is enforced by data dependency. You can't run step 3 before step 2 because step 3 needs what step 2 produces. Sequential patterns are the simplest to reason about and debug. When something goes wrong, you know exactly which step failed and what state the workflow was in.

**[03:16]** The trade-off is that sequential chains can't exploit any parallelism, and total time equals the sum of all step durations. When you're choosing between sequential and parallel, the deciding factor is always data dependency. If step B needs step A's output to function, it's sequential by necessity. If steps B and C both need step A's output but don't need anything from each other, they can run in parallel after A completes. Using sequential execution when steps are actually independent is a missed optimization. You're adding latency for no reliability benefit.

**[03:54]** But the reverse mistake is worse. Treating dependent steps as if they're parallel causes data hazards. Step B starts before it has the input it needs, uses stale or missing data, and produces wrong output. Dependency analysis has to come first. Before you decide on execution pattern, map out what each step actually needs. Parallel decomposition identifies subtasks that have no data dependencies on each other and runs them concurrently.

**[04:28]** This is where you recover the latency that sequential patterns sacrifice. If you have five independent research tasks that each take 10 seconds, sequential execution takes 50 seconds. Parallel takes 10. The design requirements are strict. Each parallel branch has to be truly independent with no shared mutable state. If two branches write to the same resource without coordination, you get race conditions.

**[04:53]** When all branches complete, a fan-in step collects results and continues the workflow. Parallel execution introduces a failure scenario. Sequential patterns avoid partial failure where some branches succeed and others don't. Your orchestration logic has to handle that explicitly with a defined policy for what happens when the fan-in collects incomplete results. Real systems combine all three patterns and seeing them together is more representative of actual architectures than studying each one in isolation. A hierarchical orchestrator might delegate to a pair of specialized sub-agents running in parallel where each sub-agent internally runs a sequential pipeline of steps or a sequential pipeline might fan out to parallel branches for a batch operation, then fan back in before the next stage.

**[05:51]** The decision at each point is local. What does this specific segment of the workflow need? Sequential, where dependencies exist, parallel where they don't, and hierarchical, where specialization justifies the layering. The most reliable architectures pick the right pattern for each segment based on its structure, not based on a preference for any one approach. Three anti-patterns show up repeatedly in agentic systems and all three are worth recognizing on site. Over-decomposition happens when you've added so many steps and handoffs that the cost of coordinating them exceeds the cost of just running the task as a single unit.

**[06:29]** The workflow spends more time passing context around than doing work. Under-decomposition is the opposite. Tasks are so large that a single failure kills the whole workflow and retry means starting from scratch, and false parallelism is the most dangerous. Treating steps with data dependencies as if they're independent, running them in parallel, and getting data hazards and silent incorrect outputs. When you see a failing system, diagnosing which anti-pattern it has tells you exactly what kind of fix is needed. A pattern isn't a preference you bring into a workflow.

**[07:06]** It's a reading of what the dependencies already are. Parallel describes steps that don't need each other. It isn't a wish for things to run faster. Confuse those two and you get false parallelism. It fails quietly and hands you the wrong answers instead of giving you what you're going for. That wraps up this one.

## 12. Sequential Pipelines — Design and Tradeoffs

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 12/136 · en_US · auto caption

**[00:00]** The focus of this lesson is sequential pipelines. In this one, we'll cover how they're structured, how to map dependencies between steps, how to design clean handoffs, where sequential execution is actually the right call, and where it quietly costs you latency when steps don't actually need to be ordered. Let's get into it. Most pipelines end up more sequential than they actually need to be, and the reason is that nobody checked what forces each step to wait. Sequential execution means tasks run one at a time in a fixed order, where each step may depend on the previous output. It's simpler to reason about than parallel execution, but it can't exploit task-level parallelism.

**[00:42]** Prompt chaining is the specific version of that pattern, where the output of one LLM call becomes the input to the next, giving each step a narrow single responsibility. And a dependency graph is the tool that tells you which steps genuinely have to come before which others, and which ones never needed to be ordered at all. A sequential pipeline is a chain where each step's output feeds forward into the next step's input. The execution order is fixed and deterministic. There's no branching by default. If step 2 depends on step 1's output, step 2 can't start until step 1 completes.

**[01:21]** That's the defining constraint. It also means the pipeline halts on failure. If any step fails, every downstream step is blocked because they have no input to work with. This is the basic structure of prompt chaining, which is a deterministic workflow technique rather than an agentic pattern. Understanding this structure is the starting point for knowing when to use it and when to break out of it. Dependency graphs are the practical tool for designing sequential pipelines.

**[01:49]** You draw an edge from step A to step B if B needs A's output to run. Steps with no incoming edges have no prerequisites and can potentially run first or in parallel with other independent steps. Steps with multiple incoming edges are synchronization points. They can't proceed until all predecessors complete. Reading the graph tells you the minimum required sequential ordering, which is often less than what your initial pipeline design assumes. Many pipelines end up more sequential than they need to be because the dependency graph was never drawn.

**[02:26]** Drawing it first is a fast way to find opportunities to reduce latency without changing correctness. Sequential execution is the right choice in four situations. First, when there's a true data dependency where step B literally needs step A's output as its input. Parallel execution won't work here. Second, when steps accumulate state where each step builds on a growing context that prior steps produced. Third, when operations need to run in a specific order like parsing before validation before enrichment.

**[02:58]** And fourth, when simplicity and auditability matter more than speed. A sequential pipeline is easy to step through, log, and debug. If you're building something where correctness and traceability are the top priorities, sequential is often the cleaner design, even if parallel would technically be faster. Let's weigh sequential strengths against sequential costs. The main cost is that total latency equals the sum of every step's latency. That's fine when steps genuinely depend on each other.

**[03:28]** It's a problem when they don't. On the other side, sequential pipelines are genuinely easier to debug. A failure in step 3 means you look at step 3's input and output and you know exactly what happened. There's no synchronization logic to reason about. No partial failures from concurrent branches. The data flow is linear and transparent.

**[03:51]** The key lesson here is that sequential is the correct pattern when dependencies are real. Choosing sequential over parallel when steps are actually independent wastes latency and is an exam trap worth knowing. Every boundary between pipeline steps needs a defined schema for what passes from one step to the next. The output schema of step n becomes the input contract for step n plus 1. Making these schemas explicit catches mismatches early before they cause runtime failures, include required fields, types, and nullability in every handoff spec. Loose informal handoffs are a common source of silent data loss.

**[04:30]** Step n plus 1 might receive a response that's missing a field it expects, silently default to a null or empty value, and continue running with corrupted data that only shows up as a wrong result several steps later. Explicit schemas give you a clear failure mode at the boundary rather than a mysterious output failure at the end of the pipeline. Error handling in sequential pipelines deserves specific attention because failures cascade. If step 2 fails, step 3 has no input and can't run. Step 4 has nothing from step 3 and can't run either. The failure propagates down the entire remaining pipeline.

**[05:16]** The cascade risk increases with depth. A five-step pipeline has more failure surface than a two-step one. Early validation at each step's entry point reduces how far bad data travels before someone catches it. Design explicit error handling at every step boundary, not just at the pipeline's final output. When a step gets invalid input, it should fail loudly and immediately rather than silently passing malformed data forward to the next step. Not every sequential pipeline has genuine data dependencies.

**[05:48]** Some are sequential purely by convention. A true dependency means step B reads a field that step A produced. The ordering is required by the data. An artificial dependency means the steps are run sequentially only because that's how the code was written, not because B actually needs A's output. Removing artificial dependencies unlocks parallel execution opportunities. Before committing to a fully sequential design, audit each step boundary.

**[06:17]** Ask whether each step genuinely needs its predecessor's output or whether it could run concurrently. That audit is often where the biggest latency wins are found without any change to correctness or reliability. There's a real difference between a step that has to wait and a step that's only waiting because that's how somebody wrote it. The first is a data dependency, and you're stuck with it. The second is just convention, and it's charging you while clock time for nothing. Once you can tell those apart, the biggest latency wins don't cost you reliability or correctness at all.

## 13. Parallel Execution — Fan-Out, Fan-In, and Synchronization

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 13/136 · en_US · auto caption

**[00:00]** In this lesson, we'll go through parallel execution patterns. We'll see how fan-out works, how to verify that branches are actually independent before dispatching them, how fan-in aggregates results at the synchronization point, what to do when some branches fail, and how the cost versus latency trade-off plays out in practice. Let's get into it. Running work in parallel is the easiest way to cut an agent's wall clock time, and the easiest way to introduce bugs you can't reproduce. Parallel execution means multiple independent tasks run concurrently. It needs a synchronization point to collect results and handle partial failures before the pipeline continues.

**[00:37]** Fan-out is the dispatch step, where a single task splits into multiple concurrent subtasks sent off all at once, and it only holds up if every branch is independent of the others. Fan-in is the synchronization step on the other side. It collects results from all the branches, deals with varying result counts and partial failures, and reassembles everything before the pipeline moves forward. Fan-out is the dispatch step in a parallel execution pattern. One control point triggers multiple concurrent subtasks all at the same time. Every branch gets its own inputs and runs independently.

**[01:17]** The branches don't have to be simple function calls. They can be full sub-agents, tool invocations, or nested workflows. The key constraint is that every branch has to be independent. Fan-out increases throughput by running work simultaneously rather than one at a time, but it only works correctly when the branches genuinely don't depend on each other. A fan-out with hidden interbranch dependencies produces incorrect results because branches might run in any order or read stale state written by a sibling branch that ran concurrently. Before committing to a fan-out design, run the independence test on every branch pair.

**[01:59]** There are three questions to ask. First, can branch B start without waiting for any output from branch A? If B needs A's output, they have a dependency and can't fan out. Second, do the branches write to shared state that could cause race conditions? If two branches both update the same record, the result depends on which one finishes last, and that's not deterministic. Third, would running the branches in any order produce the same final result?

**[02:29]** If order matters between branches, they're not independent. If any of these questions reveals a dependency, fan-out is the wrong pattern for those branches. Fix the dependency first or use a sequential design where ordering is enforced. Fan-in has four responsibilities at the synchronization point. First, it collects outputs from all branches that completed successfully. Second, it handles failures from branches that erred.

**[02:56]** Third, if the order of results matters for the next pipeline step, it reassembles outputs in the correct sequence. And fourth, it merges the collected results and passes the aggregated output to whatever comes next. Each of these has to be explicitly designed. An ad hoc fan-in that just takes whatever results are ready and throws away failures is a silent failure source. The fan-in logic is where partial failures show up, and handling them explicitly is a non-negotiable design requirement for parallel pipelines. Parallel and sequential execution have a real trade-off worth understanding clearly.

**[03:33]** Parallel execution reduces total wall clock time when branches are genuinely independent. Multiple branches run simultaneously, but it costs more in token spend per unit time and introduces partial failure scenarios that sequential execution doesn't have. Sequential execution is slower. Total time equals the sum of all step latencies, but it's cheaper per run, and there's no synchronization logic to write and no partial failures from concurrent branches. The exam trap here is worth flagging. Parallel execution introduces partial failure scenarios that sequential execution doesn't.

**[04:15]** Designing explicit handling for the case where some branches succeed and others fail is a required part of any parallel pipeline design. When some parallel branches succeed and others fail, the fan-in step has three options. First, fail the whole pipeline. Any branch failure aborts the operation entirely. This is appropriate when all branches are required for a correct result. Second, proceed with partial results.

**[04:39]** Continue with what succeeded and flag what failed. This works when partial results are still useful and the pipeline can degrade gracefully. Third, retry failed branches individually. Redispatch only the branches that errored rather than restarting the entire fan-out. Whichever strategy you choose, it has to be explicit. Silently dropping failed branches and continuing as if they succeeded is always the wrong answer.

**[05:12]** Silent failures introduce incorrect results that are extremely hard to diagnose after the fact. How fan-in merges results depends on the pipeline's purpose. Three common strategies. Voting. Multiple branches answer the same question and the majority result wins. This is useful when you want resilience against individual branch errors or inconsistencies.

**[05:38]** Concatenation. Branches produce independent outputs that are joined into a single list. Works when each branch handles a distinct segment of the input. Structured aggregation. Each branch contributes a named field to a shared output object. Useful when branches each compute a different attribute of the same entity.

**[05:56]** The key design point is to choose the merge strategy before designing the branches. The strategy shapes what each branch is expected to return, which shapes its entire design. Parallel execution cuts latency but raises token spend. When three branches run simultaneously, you're consuming roughly three times the tokens per second compared to running the same work sequentially. The total token cost is the sum across all branches, not just the longest one. Rate limits and quotas can also constrain how much concurrency is actually achievable in practice.

**[06:32]** If your API tier limits you to a certain number of concurrent requests, you may not get the latency improvement you expect from a large fan out. Model both dimensions explicitly before choosing parallel over sequential. The latency win is real, but so is the cost increase and the added complexity of synchronization and partial failure handling. So the bad outcome in production is a branch quietly writing over state another branch is still reading, and nobody catches it until an answer comes back subtly wrong. That's why independence gets tested before the dispatch, not after results land. When a branch fails, decide out loud what happens to the rest, because a silently dropped result does more damage than a slow one.

## 14. Adaptive Planning — Updating the Plan Mid-Execution

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 14/136 · en_US · auto caption

**[00:00]** When you're running agentic systems, the plan you start with often isn't the plan you finish with. In this video, we'll work through adaptive planning. We'll look at the difference between static and dynamic planning, the events that trigger a replanning decision, and how to bound those cycles so the agent stays anchored to its original goal. Let's get into it. An agent that finishes a task exactly the way it was scripted is running a static plan. Every step was authored before execution began, so nothing surprises you at runtime.

**[00:27]** Change one thing, let the model decide its next step from what it just saw, and you have dynamic planning. That shift is where adaptability comes from, and it's also where unpredictability comes from. Replanning is the narrower act inside that, revising the current plan because something failed or changed. Hold those apart in your head, because most of what makes agentic systems hard to reason about traces back to which one is in play at a given moment. These distinctions show up constantly when you're judging whether an agent is behaving correctly. The key contrast between static and dynamic planning comes down to one question.

**[01:12]** When are the steps decided? With static planning, every action is locked in at design time. You know what the agent will do before it runs. That's powerful for predictability and auditability. With dynamic planning, the model figures out the next step at inference time based on what it's seen so far. That's powerful for open-ended, adaptive tasks, but it means the sequence isn't pre-audited, and it's harder to predict or verify in advance.

**[01:36]** In practice, most production systems blend both. They use fixed structure where they can and dynamic decisions only where the task genuinely requires it. Static and dynamic planning have genuinely different risk profiles, and that's worth being explicit about. Static plans are predictable, auditable, and cost-efficient. Every step is individually testable. When something fails, you can localize it precisely.

**[02:05]** Dynamic planning gives you adaptability for goals that can't be fully pre-specified, but because next steps aren't pre-audited, the system requires stronger monitoring and fallback mechanisms to stay safe. The exam language here is important. Dynamic planning increases unpredictability, and that's a known trade-off you're accepting. The engineering response is to compensate with monitoring, logging, and explicit fallback paths rather than hoping the model stays on track. Four categories of events force an agent to reconsider the plan it is currently running. A tool call failure is the most obvious one, where the tool is unavailable or returns an error, a timeout, or an empty result.

**[02:48]** Unexpected output is subtler because the tool worked, but what came back contradicts the assumption the next step was built on. State changes are environmental, meaning something outside the agent's control shifted while it was running and made earlier steps invalid. Constraint violations are perhaps the most critical because a proposed action would cross a goal boundary or safety limit the agent is supposed to respect. Recognizing which category you are in is the first step to handling it correctly. Not every surprise requires throwing out the current plan. The decision to replan versus continue is one of the most important judgment calls in agentic design.

**[03:28]** Replanning is warranted when a core assumption the plan was built on has been invalidated. It's not warranted when the deviation is minor and the original path is still recoverable. The right question to ask is whether the original goal is still achievable via the current plan with adjustments. Unnecessary replanning wastes tokens, adds latency, and increases the chance that the agent wanders off in a new direction that only partially satisfies the original requirements. Once you've decided to replan, you need to bound the loop. A maximum iteration limit is a hard cap on how many cycles the agent gets before it escalates or stops.

**[04:09]** Without it, an agent that keeps hitting the same obstacle will loop forever. A goal constraint check validates that each revised plan still satisfies the original task before execution resumes. That check is what prevents goal drift, which is the subtle failure where the agent solves the immediate obstacle and quietly stops serving the actual goal. Loop termination follows from both. Stop at the cap or stop when the new plan clears every constraint. Preserve the original goal as a persistent artifact and log each revision against it so drift is detectable after the fact.

**[04:47]** The failure I worry about here isn't an agent that crashes. It's one that quietly beats the obstacle in front of it and stops serving the goal that you actually gave it from the start. Revision after revision, the original intent fades out of the run. A hard cap on cycles plus a constraint check before execution resumes is what holds everything in place. ## 15. Handling Ambiguity and Incomplete Specifications

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 15/136 · en_US · auto caption

**[00:00]** If you're building agents that interact with real users, ambiguous goal specification is unavoidable. We'll spend the next few minutes going over the two core strategies for dealing with unclear instructions, how iterative refinement loops close quality gaps, and why documenting assumptions matters for human oversight and auditability. Let's get into it. What should an agent do when the instruction it was handed can be read several different ways? That's an ambiguous goal, a task specification that doesn't fully define the expected outcome, and leaves the agent to pick an interpretation. The response is either clarify first or assume and proceed.

**[00:41]** Clarify first means pausing execution and asking a human for more information, which costs latency but protects you when a wrong reading would be expensive. Assume and proceed means making a reasonable inference and continuing, which is the right call for low stakes, reversible, or time-sensitive work. The whole skill is knowing which response fits the situation in front of you, and that's what we're building here. Some situations make assumption-based execution genuinely risky, and those are the cases where clarifying up front is the right call. Irreversible actions are the clearest example. If the agent is about to delete data, send an external communication, or commit a transaction that can't be undone, a wrong assumption could cause significant harm.

**[01:29]** High-cost operations are similar. If a task triggers an expensive API call or a long batch process, it's worth a brief delay to confirm the scope is right. Scope uncertainty is the third signal. When the agent doesn't know what's in bounds, wrong assumptions don't just cause minor errors. They cause the agent to operate on entirely the wrong data or system. On the flip side, clarifying every ambiguity makes agents slow, brittle, and frustrating to work with.

**[01:59]** The assume-and-proceed strategy is appropriate when the action is low stakes and easily reversible. If the agent makes a wrong call, the user can undo it without much cost. Time-sensitive tasks are another case. Sometimes the window for action is narrow enough that waiting for clarification means missing the opportunity entirely. And sometimes the context is clear enough that the right interpretation is obvious, even if the instruction wasn't perfectly worded. The goal isn't maximum caution.

**[02:30]** It's appropriate judgment based on actual risk, and that judgment needs to be calibrated to the real costs involved. It helps to put the two strategies directly side-by-side. Clarifying up front adds latency and requires the human to be available and responsive. It's justified when getting it wrong would cause irreversible damage, trigger high costs, or send the agent off into the wrong scope entirely. Assuming-and-proceeding maintains task velocity and doesn't require human involvement. It's justified when the action is reversible.

**[03:04]** The stakes are low, and the context makes the intent reasonably clear. Neither strategy is universally better. The right answer is always situational, and agents that apply the same strategy to every ambiguous instruction will get it wrong in one direction or the other more often than they should. Three practical criteria help structure the clarify-versus-assume decision. Reversibility is probably the most important. If the action can be undone easily and cheaply, proceeding on an assumption carries much lower risk.

**[03:38]** Stake level is second. High-cost or high-impact operations justify the latency of a clarification request in ways that routine, low-cost tasks don't. Scope clarity is third. When the boundaries of the task are genuinely ambiguous, a wrong assumption doesn't just affect this one action. It can cause the agent to work on the wrong data or the wrong system for an extended sequence of steps before the error surfaces. Clear scope reduces that cascading risk significantly.

**[04:11]** When a single pass isn't good enough, iterative refinement is the pattern that closes the gap. A generator agent produces a candidate output. An evaluator agent, which might be a separate model or just a structured critique prompt, scores that output against a rubric and returns specific feedback rather than a bare pass or fail. The generator takes that critique and produces a revised version. Convergence criteria decide when the loop stops. Either the quality bar is met or the maximum iteration count is reached.

**[04:42]** That cap isn't optional. Without it, the loop can run indefinitely on tasks where the evaluator is hard to satisfy. This is called the evaluator-optimizer loop, and it earns its cost on work like writing and analysis, where quality is hard to specify up front but easy to recognize. When an agent proceeds on assumptions, the best practice is to make those assumptions explicit in the output or the execution log. This isn't just a courtesy. It's a meaningful audit capability.

**[05:13]** A human reviewer can check whether the assumption was reasonable without rerunning the full task from scratch. Well-documented assumptions reduce audit burden, speed up review cycles, and make the agent's reasoning transparent enough to catch problems before they compound. The longer-term solution is to improve goal specification design at the source. Precise, well-scoped instructions reduce the number of assumptions agents need to make in the first place. That's a design investment that pays off across every task that touches that specification. It's fun to treat vague instructions as a challenge for how reliable your system is.

**[05:52]** If something is cheap to undo, the agent should just move forward. If something is expensive or permanent, it should stop and ask permission. That single question carries most of the judgment here. It only holds up if the agent writes down what it assumed because a reviewer can't check reasoning that was never communicated.

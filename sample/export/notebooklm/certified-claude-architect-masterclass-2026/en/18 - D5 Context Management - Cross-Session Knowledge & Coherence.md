## 120. The Scratchpad Pattern — A Durable Memory Slot

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 120/136 · en_US · auto caption

**[00:00]** This lesson covers Scratchpad files, and although it's late in the course, it is critically important to understanding how Clodd operates. Every new Clodd code session opens with zero memory of past work. A Scratchpad file is the repo that solves that. We'll look at the problem, what to put in the file, what to keep out, and how to enforce the habit of reading and writing consistently. Let's get into it. A Scratchpad file is just a plain text file in the repo, typically named notes.md or context.md, and it is the entire mechanism for carrying work across a context reset.

**[00:40]** What it holds is cross-session knowledge, the category of information that should survive that reset. Decisions you have made, dead ends you have already explored, naming conventions your team has agreed on. Inside it, a decision log is a dedicated subsection for architectural choices and their rationale. The decision log matters most because without it, a future session will re-examine a question you already resolved. All three of these are practical tools, not just vocabulary, and together they define what a Scratchpad is trying to accomplish. Here is the core problem.

**[01:14]** When a new Clodd code session starts, the context window is completely blank. The agent has no memory of what happened in the previous session. That sounds like a minor inconvenience, but it compounds quickly. The agent will re-explore dead ends you already ruled out. It will re-ask questions you already answered. It will make naming choices that contradict decisions from earlier sessions.

**[01:38]** Every session effectively starts over, which means you are paying the cost of discovery work repeatedly instead of once. The Scratchpad file is the practical fix for this. It is a lightweight mechanism to carry knowledge forward across the boundary that the context window creates. The cost of maintaining a Scratchpad is low. The cost of not having one grows with every session. Think of it as two workflows, side by side.

**[02:01]** In the no-Scratchpad workflow, each session starts from scratch. The agent doesn't know about the dead ends, doesn't remember the agreed naming conventions, and may contradict earlier architectural decisions without realizing it. That drift accumulates across a long project. In the with-Scratchpad workflow, the agent reads the file at the start of the session, picks up current task state, respects recorded decisions, and avoids already explored dead ends. Before the session closes, it writes updates. The gap between those two workflows gets wider the longer a project runs.

**[02:39]** A single day of work without a Scratchpad is manageable. A week or a month of work without one is genuinely painful to reconstruct. What belongs in the Scratchpad? Think of it as the evolving layer of your project. The Scratchpad holds things that change run-to-run. First, architectural decisions and the reasoning behind them.

**[02:59]** If you decided to use a particular data structure, a particular API shape, or a particular file layout, record that choice and the why. Second, dead ends. If you tried an approach and it didn't work, write that down so the next session doesn't waste time on the same path. Third, naming conventions. If a term has a specific meaning in this codebase, state it. Fourth, current task state.

**[03:22]** What is in progress? What is blocked? What the next action is? These four categories cover most of what persistence actually needs to capture. Just as important as knowing what to include is knowing what to leave out. Three things don't belong in the Scratchpad.

**[03:41]** First, code. The codebase is where code lives. Copying snippets into the Scratchpad creates a second source that drifts from the actual implementation. If you need to reference code, point to the file, not the content. Second, credentials. Secrets, tokens, and API keys should never appear in a plain text file that gets committed to the repo.

**[04:04]** That is a security boundary, not a style preference. Third, private user data. Any personal or sensitive information has no place in a shared Scratchpad. Keeping the Scratchpad focused on workflow state, not content, also makes it easier to prune and maintain over time. Reading the Scratchpad at session start sounds obvious, but it requires explicit enforcement. Left to default behavior, an agent won't automatically seek out a file you haven't told it about.

**[04:34]** The most reliable approach is to list the Scratchpad in clod.md as one of the first files to read at session start. That puts the instruction in a place the agent checks reliably. A more automated approach is a session start hook that surfaces the file before any user message is processed. Either approach works. What doesn't work is assuming the agent will find and read the file on its own. The read has to be mandatory, not optional, and the mechanism has to enforce that consistently every session.

**[05:04]** The write half of the discipline is as important as the read half. Before you close a session, the agent should update the Scratchpad to reflect what happened. That means recording decisions made during the session, noting any dead ends reached, and updating the current task state block so the next session knows where to pick up. A session end hook runs on termination for cleanup, but it can't block, so the write stays instruction-driven and depends on habit. One detail worth emphasizing is that a stale Scratchpad is worse than no Scratchpad. If the agent reads an outdated file and trusts what it says, it will act on information that no longer reflects reality.

**[05:44]** The read and the write are a pair, and both have to happen reliably. The Scratchpad puts memory in the repo instead of inside the model. The habit that makes it pay off is writing the file for the next session, not for yourself. If it doesn't say what got decided and what was already ruled out, tomorrow's session starts cold and quietly re-does all of your work. That closes out this session. I'll see you in the next one.

## 121. Designing a Healthy Scratchpad — Hygiene and Limits

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 121/136 · en_US · auto caption

**[00:00]** In this lesson we'll go through keeping a Scratchpad healthy. Writing one is the easy part. Maintaining it over days and weeks is where most projects fall short. We'll cover length discipline, structure, pruning policy, how to handle conflicts with Cloud.md, multi-developer coordination, and privacy boundaries. It's a lot to go over, so let's get into it. A Scratchpad earns its keep only while it stays accurate.

**[00:28]** Scratchpad hygiene is the discipline of keeping the file accurate, pruned, and consistently structured. It isn't a one-time setup task. It is an ongoing practice that has to happen every session. Then there is the boundary between Cloud.md and the Scratchpad, which is the most important conflict to understand. Cloud.md holds stable rules that apply across all sessions, while the Scratchpad holds evolving session state. When they say different things, Cloud.md wins, and that priority needs to be explicit in how you configure the agent.

**[01:03]** Pruning policy is the defined rule for what gets removed and when. Without a policy, nothing ever leaves the file, and it grows into a record of every thought anyone ever had about the project, including the wrong ones. Scratchpads bloat fast. Every session adds entries. Sessions that resolve items rarely take the time to remove the old ones. Over a week of active work, a Scratchpad that started at 50 lines can easily reach 500.

**[01:32]** At that length, it is slower for the agent to process and harder to reason over. The fix is a cap with a pruning trigger. Pick a threshold and treat crossing it as a signal to do a pruning pass before adding more content. Remove entries that are fully resolved. Archive completed task state to a separate history file if you need a record. Rewrite the current state block rather than appending to it.

**[01:57]** These habits together keep the file at a useful size and prevent it from becoming an obstacle instead of an aid. Structure matters because it makes the file scannable for both you and the agent. I recommend four blocks. First, dated entries at the top, with a timestamp on each so you can identify stale notes quickly during a pruning pass. Second, a decision log for architectural choices and their rationale. This block changes rarely because good decisions have a long, useful life.

**[02:28]** Third, a current state block that gets rewritten each session rather than appended to. This is the block that tells the next session exactly where work stands right now. Fourth, an open questions block for unresolved issues the next session needs to address. When a question is answered, the entry comes out. These four blocks give the Scratchpad a shape that stays manageable even under active, sustained use. Let's be precise about the boundary between clod.md and the Scratchpad.

**[02:59]** Clod.md holds stable rules. Coding conventions, tool permissions, standing instructions about how the agent should behave. These change rarely and represent the settled state of the project. The Scratchpad holds evolving session state. What is in progress? What decisions were made this session?

**[03:15]** What questions are open? These change every session. When the two contradict each other, clod.md takes precedence. This priority needs to be explicit in the clod.md itself. Something like, the Scratchpad records session state, and in case of conflict, these rules apply. Without that explicit hierarchy, the agent may try to reconcile the two in unpredictable ways.

**[03:43]** Make the precedence rule visible and unambiguous so there is no room for misinterpretation. When a Scratchpad is committed to Git, it becomes a shared resource across the team. That is mostly a good thing. Developers can read each other's session state, see decisions that were made without them, and avoid re-exploring dead ends their colleagues already documented. But shared Scratchpads introduce coordination overhead. Merge conflicts on the Scratchpad signal that two people worked on the same task concurrently, which is worth knowing.

**[04:18]** The current state block needs clear ownership when two developers are working in parallel. A simple convention is that whoever is driving the active task owns that block. For small teams with clear task ownership, one Scratchpad per repo works well. Larger teams with parallel workstreams may want per-developer or per-feature Scratchpad files instead. Privacy is an active choice, not a default. Before you commit the Scratchpad, review what it actually contains.

**[04:50]** This sounds obvious, but under deadline pressure, people paste things into the Scratchpad quickly without thinking about commit safety. Credentials, tokens, and API keys should never appear in a committed file. If the nature of your work means the Scratchpad frequently contains sensitive context, add it to .gitignore and treat it as a local-only file. Document that choice explicitly in clod.md so future developers know the Scratchpad isn't tracked. The tradeoff is that a git-ignored Scratchpad can't be shared via git. You lose the team coordination benefit.

**[05:26]** Make that tradeoff consciously and explicitly rather than discovering it after a credential ends up in a commit. The graveyard failure mode is the most common way Scratchpads go wrong. It happens when entries accumulate without removal. The file grows into a record of everything that was ever true about the project, including things that are no longer true. The agent reads the file and treats all of it as current. Stale notes propagate into decisions.

**[05:56]** The agent recommends an approach you already ruled out or references a naming convention you changed weeks ago. The agent isn't being careless. It is doing exactly what it should. Trusting the authoritative state file, you gave it. The problem is that the file stopped being authoritative. Avoiding the graveyard requires consistent pruning discipline.

**[06:19]** Without it, the Scratchpad eventually does more harm than good. A healthy Scratchpad requires active maintenance, not just initial setup. Cap the length, prune resolved entries every session, and rewrite the current state block rather than appending to it. Keep the structure consistent so the file stays scannable for Claude. Keep credentials out of anything that you commit, and let Claude.md win whenever the file and the rules disagree. That's it for this lesson.

## 122. Why Delegate Discovery to a Subagent

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 122/136 · en_US · auto caption

**[00:00]** In this video, we'll work through why discovery work belongs in a sub-agent, not in your main agent's context window. We'll cover what makes discovery so verbose, how the delegation pattern keeps things clean, and the cases where spawning a child agent is worth it versus cases where it's overkill. Let's get into it. Ask an agent to find the authentication flow, and it will read a dozen files you never wanted in your context. Sub-agent delegation is the pattern that fixes that. You spawn a child agent to handle the verbose investigation, and it returns only a focused summary to the parent.

**[00:38]** Discovery is the activity itself, finding relevant files, documentation, or context inside a large codebase or knowledgebase. And disposable context is the sub-agent's context window. It holds all the messy intermediate state, every grep result, every dead-end file rid, every candidate that turned out to be wrong, and all of it is discarded the moment the sub-agent returns its answer. Let's start with why discovery is so naturally verbose. When you ask an agent to find the authentication flow in a large codebase, it doesn't just open one file. It searches.

**[01:14]** It reads candidates. It hits dead ends. Grep results come back with dozens of matches, most of them irrelevant. Each file it opens lands in the context window, whether or not it turns out to be useful. By the time the agent finds the right file, its context holds pages of noise, on top of whatever task work it was doing before. That pollution is the core problem delegation solves, and the reason isolating discovery matters so much.

**[01:43]** Compare inline discovery to delegated discovery directly. When the main agent reads files itself, every grep result and every dead-end accumulates in its context. Useful state competes with noise as the session continues, and the more files the agent touches, the worse that crowding gets. With delegation, the main agent hands the question to a sub-agent. The sub-agent investigates, then returns only its finding. The main agent acts on that finding without ever seeing the raw reads.

**[02:15]** The verbose intermediate state never crosses the boundary. It lives inside the sub-agent's context, and it disappears when the sub-agent finishes. The parent context stays clean for the duration of the task. The delegation pattern has four concrete steps. First, the main agent frames a precise discovery question and defines the shape of the answer it needs. Second, the sub-agent receives that question along with a minimal tool palette.

**[02:46]** Third, the sub-agent investigates and produces a structured summary. Fourth, the main agent reads the summary and continues its work. Nothing else crosses the boundary. The sub-agent doesn't return file contents. It doesn't return grep output. It returns an answer in the shape the main agent asked for.

**[03:06]** That shape is called the return contract, and it is what makes the pattern reliable across different types of discovery tasks. Three scenarios make delegation clearly worth the overhead. Code-based surveys, where finding an answer requires reading many file candidates before you can narrow down to the right one, benefit enormously from isolation. Dock spelunking through long reference documents or changelogs, where most pages are irrelevant to the question at hand, is a strong second case. Multi-step lookups, where you chain several searches before a conclusion emerges and each step generates its own layer of intermediate results, are the third clear case. In all three situations, the volume of intermediate state is high enough that isolating it in a sub-agent pays for the overhead quickly.

**[03:57]** Not every lookup justifies spawning a child agent. Sub-agent delegation adds real overhead in the form of latency, token cost, and coordination work between agents. If you already know the file path, read it in line. If the answer lives in a short document with an obvious location, don't spawn a sub-agent to find it. Single-file lookups are the clearest case where the overhead outweighs the benefit. There isn't a clean numeric threshold here.

**[04:25]** Delegate when the exploration would dump file contents into your context that you won't reference again. The benefit grows as the investigation spans more candidate files and more dead ends. The delegation trade is straightforward once you see it clearly. You spend sub-agent cost, and you buy main agent clarity. The sub-agent run adds latency and token spend. In exchange, the main agent avoids context pollution and stays focused on the actual task, rather than drowning in discovery noise.

**[04:57]** Whatever comes back is a hypothesis the parent should verify when the stakes are high, because a sub-agent can miss a file or misread a signature. The net benefit still grows as the discovery gets more complex. For large investigations across many files, the trade is almost always favorable. For trivial lookups, it isn't. Discovery is verbose by nature, and handled inline, it pollutes the main agent's context until the useful state gets buried. Delegating to a sub-agent isolates that verbosity in a disposable context that disappears when the child returns its findings.

**[05:34]** The pattern pays off for complex, multi-file investigations, and when you already know the path, a plain inline read is simpler. That wraps up this lesson. I'll see you in the next one.

## 123. Delegation Mechanics — Prompts, Returns, and Failure Modes

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 123/136 · en_US · auto caption

**[00:00]** Let's spend a few minutes going over the mechanics of sub-agent delegation, writing a precise prompt, defining a return contract, scoping the tool palette, and recognizing the failure modes that undermine the whole pattern. Getting delegation right in practice means knowing all four of these pieces, not just the high-level idea. Let's work through each one. Delegation succeeds or fails on the shape of the handoff. The return contract is the explicit shape of the response the sub-agent produces, defined up front so the parent's context stays clean after the sub-agent returns. The trust boundary is the architectural rule that the parent treats sub-agent output as a hypothesis, to verify, not a definitive truth.

**[00:47]** And sub-agent delegation is the pattern itself, spawning a child agent to perform verbose investigation and returning only a focused summary. The mechanics in this lesson all exist to make those ideas work reliably in a real system, not just as an abstract design principle. Start with the prompt. A sub-agent prompt is a precise question, not an open-ended task, and a well-formed one specifies four things. The question, stated as a single concrete ask, rather than a broad directive. The scope, naming which directories or file types to search and which to ignore.

**[01:26]** The return shape, describing exactly what format the answer should take. And the stop condition, telling the sub-agent when to return what it has, rather than continuing to search. Without a stop condition, a sub-agent can spin on a hard lookup and return late with more information than the parent needs. Vague prompts produce vague answers that re-pollute the parent's context, so the quality of the outcome tracks the quality of the prompt you write. Compare a vague prompt to a precise one directly. A vague prompt says, find the authentication logic and explain how it works.

**[02:02]** The sub-agent reads broadly, follows tangents, and comes back with a narrative. The parent receives a wall of text. Context is polluted. A precise prompt says, return the file path and function name that handles JWT validation in one file path and one function name, with one sentence of context, nothing else. The parent gets exactly what it needs. The difference between those two prompts is the entire difference between delegation working and delegation failing to deliver value.

**[02:35]** The return contract is the specification for what the sub-agent hands back. A structured finding beats a narrative every time. A strong default shape is, file path, line number, brief summary. That gives the parent enough to act on without loading it with content it didn't ask for. You should also specify a maximum length explicitly in the prompt. Without a length cap, a sub-agent that found something interesting has no guidance about how much to return.

**[03:03]** A well-defined contract keeps parent context clean, regardless of how much the sub-agent read during its investigation. The contract is the guardrail. Scoping the sub-agent's tool palette is the third mechanical decision. Give the sub-agent enough tools to investigate, and no more than that. Read tools and search tools belong on the palette. Write tools, delete tools, and API call tools generally don't.

**[03:30]** The sub-agent's job is to find things, not to change them. A narrow palette prevents accidental side effects during discovery, and keeps the sub-agent's behavior predictable and auditable. If you let a discovery sub-agent write files or make API calls, you have turned a low-risk investigation into something with real consequences. Keep the palette small and read-only as the default. The trust boundary is the rule that the parent treats sub-agent output as a hypothesis, not a verified truth. Sub-agents can be wrong.

**[04:06]** They can misread a function, miss a file that overrides the one they found, or return a stale result from a cached document. For low-stakes lookups, proceeding directly on the sub-agent's answer is usually fine. For critical path decisions, like identifying the function you are about to modify, or the config you are about to update, the parent should spot-check the finding before acting. Calibrating how much trust to extend based on what is at stake is the practical skill the boundary concept is really about. Three failure modes show up repeatedly in practice. The first is a wall-of-text return, where the sub-agent ignores the return contract and sends back a narrative.

**[04:49]** This re-pollutes the parent's context and defeats the whole purpose. The second is scope creep, where the sub-agent reads beyond the specified scope and returns extra findings the parent didn't request, adding noise and latency to the interaction. The third is blind trust, where the parent acts on sub-agent output, without verifying critical findings, and propagates errors into downstream work. All three failures trace back to the same root cause, insufficient specification in the original prompt. Tight prompts and clean returns is the idea to carry forward here. The return contract carries most of the weight, because an uncapped answer walks the same verbosity right back to the context you delegated to protect.

**[05:34]** A sub-agent isn't a smaller you, it's a narrow question with a shape on the answer, and whatever comes back is still a claim worth checking. Keep that in mind. That wraps up this lesson. I'll see you in the next one.

## 124. Long-Conversation Coherence, Compaction, and Session Memory

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 124/136 · en_US · auto caption

**[00:00]** When a multi-turn conversation runs long enough, it eventually hits a context window limit, and without active management, the model loses earlier instructions and established facts. Over the next few minutes, we'll cover how that pressure builds, what compaction strategies reduce it, how different memory patterns keep the model grounded, and what coherence techniques prevent goal drift. Let's get into it. Every turn you add to a conversation costs tokens you never get back, and that simple fact drives everything in this lesson. Context window pressure is what happens as a conversation accumulates turns and the token count approaches the model's limit. Conversation compaction is the strategy of periodically summarizing or compressing earlier turns into a shorter representation.

**[00:50]** It reduces token consumption while preserving the essential thread, and it's lossy by design, which is an important constraint. Session memory is the broader category covering any mechanism that persists conversation state, whether that's everything inside the context window or summaries and facts stored externally and retrieved on demand. These mechanisms interact constantly in production systems. Let's be precise about how context window pressure actually builds. Every turn in a multi-turn conversation appends new content to the history. User messages, assistant replies, tool results, all of it accumulates.

**[01:29]** On top of that, the system prompt and any tool definitions consume tokens on every request. That reduces how much space is available for conversation history. When the window fills, older turns get truncated, or the request fails. This is a different problem from the lost-in-the-middle effect we covered earlier in the course. That problem is about position-based attention degradation. Content in the middle of a long context gets attended to less effectively than content at the edges.

**[01:59]** Context window pressure is different. It's about accumulation and eventual truncation of content that no longer fits at all. Both are real problems, but they require different solutions. Here's something worth knowing. The model isn't flying blind about how full its context is. Claude gets signals about its own context state.

**[02:20]** At the start, an injected token budget tag tells the model roughly how much room it has to work with. And during agentic runs, after a tool call returns, the system can inject a warning noting that context is filling up. Together, these cues let the model pace itself. It can summarize what it has, wrap up a line of work, or hand off before it runs out of room, rather than charging ahead until it truncates. The important caveat is that this is a signal, not a hard guarantee. Awareness makes good behavior more likely, but your system still needs real management.

**[02:55]** Don't treat the model's self-awareness as a substitute for a budget you enforce in code. The first architectural decision in any long conversation system is where memory lives. In-context memory keeps everything in the active conversation. It's simple. There's no retrieval step, no external system to maintain, and the model has direct access to every turn. The constraint is the context window.

**[03:21]** Once the conversation grows beyond what fits, something gets cut. External memory moves summaries, key facts, or user preferences into a database. Relevant fragments are retrieved and injected at the start of each turn, similar to how RAG works for document retrieval. Retrieval memory scales well beyond any context window and enables multi-session persistence. The tradeoff is retrieval complexity. You need a retrieval mechanism, and you need to decide what to store and when.

**[03:53]** Most production systems land somewhere between these two extremes. Compaction is how you extend the useful life of in-context memory by reducing how much space earlier turns consume. There are three main strategies full summarization replaces all prior turns with a single concise summary. It's the most aggressive reduction but loses the most detail. Selective summarization keeps key decisions and outcomes while discarding small talk, filler turns, and intermediate reasoning. It's a good middle ground for most use cases.

**[04:27]** The sliding window approach retains the last n turns verbatim, giving the model precise access to recent context, and prepends a summary header covering everything before that window. This preserves recency precision while still capping total token consumption. The right strategy depends on what the conversation type actually requires. Not every session needs the same approach. Compaction is a powerful tool, but it has a clear failure mode, applying it where verbatim history is required. A code review conversation is the obvious example.

**[05:01]** If the model compacted away an earlier code snippet, it can no longer reference it accurately later in the session. Legal and compliance conversations are another case where verbatim records matter, and lossy compression is inappropriate. On the positive side, compaction fits well in customer support flows, long, open-ended research sessions, and personal assistant interactions. These are cases where you need topic continuity but don't need to re-quote exact earlier outputs. The design decision is simple. What's the worst thing that could happen if an early turn detail is lost?

**[05:37]** If the answer is significant, don't compact that conversation. If the general thread survives fine, compaction is appropriate. The hybrid memory pattern is the most practical approach for production systems that need both recency and long-term continuity. The structure is straightforward. Inject a session summary header at the top of each new API call. This summary covers the overall goals, key decisions, and established facts from earlier in the conversation.

**[06:07]** Then keep the last n turns verbatim in the active context so the model has precise access to recent exchanges. Persist the summary between sessions so a user who returns days later resumes with grounded context rather than starting from scratch. This pattern works well for personal assistants, long-running agents, and any system where users return to ongoing threads. It also pairs naturally with prompt caching. Caching the static summary header across turns can meaningfully reduce per-turn costs. Even when the full conversation fits within the context window, long sessions drift without active coherence management.

**[06:49]** The model can subtly shift away from the user's original goal as new topics accumulate. Three techniques address this. The session header pattern means opening each API call with a brief summary of prior context, grounding the model before the new turn begins. Explicit state tracking has the model maintain and update a structured JSON state object, capturing current goals, established facts, and decisions made. This state becomes part of the prompt on each turn, giving the model a structured anchor. Goal anchoring restates the user's original goal at the start of each turn.

**[07:26]** It's the simplest technique and often the most effective for multi-step workflows, where scope creep is the primary risk. The right memory strategy depends on conversation type. Short session use cases like customer support need coherence within one session only. The exchange is bounded, the goal is well-defined, and in-context memory usually handles it as long as turns stay within a reasonable count. Long-session use cases are the opposite extreme. External assistance and multi-session workflows have users returning across sessions expecting continuity, so external memory or hybrid patterns are required.

**[08:05]** Code copilots sit in the middle. They need precise verbatim access to recent code, so selective compaction is fine for non-code context, but risky for code artifacts. Choose the memory strategy based on what the conversation type actually needs, not on what's easiest to implement. Going out of room and losing the thread are not the same problem. Compaction fixes the first. It buys you tokens back by trading away detail you can't get back.

**[08:34]** Drift is the other, and it happens inside a window that still has plenty of space left. Anchoring the goal is what fixes it. Reach for the wrong one, and you'll compress a conversation that was never short on room and just needed an anchor. That brings this one to a close. I'll see you in the next video.

## 125. Server-Side Compaction

> Course: Claude Certified Architect (CCAR-F) - 2026 Exam Prep · Lesson 125/136 · en_US · auto caption

**[00:00]** Every long conversation runs into the same ceiling. A session eventually fills the token space the model can read. For the next few minutes, we'll dig into server-side compaction, the API's own opt-in version, not the compact command inside Cloud Code. We'll see what it does, how it differs from your own rolling summary, and one habit that protects your facts. Let's dig in. A conversation isn't storage.

**[00:24]** Everything the model can see right now sits inside the context window, the fixed span of tokens it reads at once, and every message you send, every tool call, and every tool result eats into it. Compaction is a server-side step that kicks in once you cross a token threshold you set. By default, it summarizes the whole conversation so far into a compact form, then lets the session continue from that summary. Durable state is the one I care about most. That's any fact you deliberately store outside the conversation in a file or a database, so it survives no matter what happens to the transcript. Everything ahead builds on that last one.

**[01:05]** So what does compaction actually do? First, it's opt-in. You turn it on with a beta header and a context management strategy, and you set the trigger threshold, which defaults to 150,000 input tokens and can go as low as 50,000. Once it's enabled, the platform does the rest automatically. When the session reaches that threshold, by default it summarizes the whole conversation up to that point and distills it into a compact block, then continues from that summary. It doesn't keep your recent turns word-for-word unless you opt-in.

**[01:41]** There's a client-managed setting, pause after compaction, where your own code reinserts the recent messages verbatim. But that's on you to wire up, not automatic. From your seat, you keep talking to the model exactly as before. Why does this feature exist at all? Because every long agent run collides with the same wall. Extended chats and multi-step agent runs fill the window fastest, so that's where this earns its keep.

**[02:11]** The window is finite, old turns pile up, and eventually they crowd out room for new ones. Without some kind of help, a session just stalls once the history overflows the space available.
